# provider 与账户

<a id="providers-and-accounts"></a>

网关可以把请求发往三类上游：

- `providers.json` 里的一个 **provider**：一个带一个或多个 API key 的端点。Google Vertex AI 的那个没有 key：它是用用户的 Google 凭据签名的。
- 一个 **订阅账号**：星鸣自己签入的账号（Codex PKCE、Copilot 设备码、Google OAuth），或者由 plugin 提供的账号。星鸣不再读取任何别家 Agent 的登录态。
- 一个 **plugin 的账号**：由 OpenCode plugin 提供的订阅。

包 `internal/provider` 装着这三者、建在它们之上的路由组，以及各自剩下的额度。

已废弃的内置订阅的 plugin 归属在[provider 与 plugin 归属](provider-plugins.md)里。网关如何在每次请求里排列 key 和账号，在[网关路由与故障转移](gateway-routing.md)里。

## 远端星鸣

<a id="remote-starling"></a>

`remote-starling` 预设属于自己的一类，`KindRemote`（`remote`），不是中继：app 的添加面板把它列在 "Another computer's Starling" 下面，在 "On this machine" 之后，`starling presets` 和 TUI 的添加列表也同样这样叫它（[`tui/pages.go`](../../internal/tui/pages.go) 里的 `kindNote`）。

一个 `remote-starling` provider 从一个地址推导出 Chat、Responses、Messages 和 System One 的 base（[`remote_starling.go`](../../internal/provider/remote_starling.go) 里的 `remoteStarlingEndpoints`）。它的模型列表用 `X-Starling-Drawers`、`X-Starling-Videomakers` 和 `X-Starling-Deciders` 请求图像、视频和决策。网关只在被问到时带上它们，`kind` 是 `image`、`video` 或 `decision`。决策条目会经过 `keyAllowed`，包括模型和账号的限制。[`catalog/live.go`](../../internal/catalog/live.go) 保留每种 kind 以及远端已经公开的所有模型，包括检索模型。这份共享列表没有单独的检索 kind：这些条目仍然留在 `Catalog` 和 agent 的模型列表里，就像在远端一样。保留它们让检索路由成为可能；它们的存在并不表示它们支持对话。

`DecidesModel` 用远端明确的决策标记，所以 Clef 和自定义名字都行，而一个叫 Jev Router 的对话模型仍然是对话模型。`Deciders` 列出这些决策，网关也回答它们，即使用户本地的对话挑选里没有。路由组的挑选器、模板和 TUI 提供的是 `OfferedDeciders`：存下了挑选时，只有被挑的决策模型，加上组已经点名过的那些，而供应商编辑器把其余的显示成没被挑（coeo91 报告：挑了两个免费的 OpenRouter 模型，OpenRouter 的决策模型仍然在它们旁边被提供）。只有远端的决策条目用 `entryFor` 来套用用户的模型名和限制；别的决策 provider 保持它们之前的条目格式。编辑器在 [`providers.go`](../../internal/gui/providers.go) 里的 `providerInfo` 在远端没有决策时发送 `deciders: []`，从而抑制 UI 那套靠名字猜的老逻辑。编辑器只提供一个远端地址；它的 System One 端点由那个地址推导出来，没有单独的输入框。没有名字的决策用它们的模型 id 作显示名和 provider 标签。刷新会换掉整份列表：被移除的决策不再路由，而一份空的远端列表绝不会凭空多出一个 Jev 别名。
没有决策列表扩展的旧对端继续服务它的其它 API，但必须更新之后它的决策才能被发现。见 [`decide.go`](../../internal/provider/decide.go)。

oMLX（#1641）和 MLX-Serve 也是这样的混合 provider：oMLX 的服务器把 Clef、Clef-Flash 和 OpenJev 混在它的对话模型里列出，没有任何东西能区分它们，所以它的决策模型是 `/v1/models/status` 给出 `model_type` 为 `decision` 的那些，按 `/v1/models` 用的那个名字（它的别名），像 OpenRouter 那样存在 `<id>.decisions` 下（[`omlx_decide.go`](../../internal/provider/omlx_decide.go) 里的 `omlxDecides`、`listedOMLXDecide`）。MLX-Serve 在它的 `/v1/models` 里用 `capabilities: ["decisions"]` 标出它们，存在 `<id>.decisions` 下（[`mlxserve_decide.go`](../../internal/provider/mlxserve_decide.go) 里的 `mlxServeDecides`、`listedMLXServeDecide`）。Ollama 和 Ollama Cloud（Nanka 报告；Ollama 0.35.0+，云模型要 0.40.5+）在它们的对话 API 旁边于 `/v1/systemone` 提供 System One，并像别的 provider 一样在 `/v1/models` 里列出决策模型（Tev、Nimble、Clef）。它们的 `/api/tags` 用同一个 key 问，给出每个模型的 `capabilities`，这些是 `decision`，而能读图像的是 `vision`。它们被存在 `<id>.decisions` 下，列表没给窗口时云版用它的 65,536 token 窗口（[`ollama_decide.go`](../../internal/provider/ollama_decide.go) 里的 `ollamaDecides`、`listedOllamaDecide`）。比它的 System One 更老的 Ollama 不列 capabilities，所以也没有。一个什么都不列的服务器就什么都不列，也不会为它编出一个 Jev。一个在预设有了决策 base 之前就存下来的 oMLX、MLX-Serve 或 Ollama provider，会把它的对话 base 当成决策 base。

CLI 和 TUI 会为远端以及其它混合 provider（像 OpenRouter，同时服务对话模型和决策模型）报告模型列表取回的错误。只有一个只做决策的 provider 保留那套单独的决策发现行为（[`providers_cli.go`](../../internal/cli/providers_cli.go) 里的 `announce`、[`tui/pages.go`](../../internal/tui/pages.go) 里的 `addKeyAsk`）。一个远端的端点测试会复用成功的模型发现结果作为它的决策结果，而在没有发现任何决策模型时报告没有（[`test.go`](../../internal/provider/test.go) 里的 `Test`）。

账号发现（#1535）这一整层机制已从星鸣移除：不再有开关，也不再有环境变量。设置 → 隐私 → *订阅账号*、`starling accounts discovery off` 和 `STARLING_NO_ACCOUNTS=1` 都不存在了，`noAccountDiscovery` 这个设置项和 `settings.AccountDiscoveryOff` 也没有了。星鸣不读任何别家 Agent 的登录态：不读它们的凭据文件（`~/.claude/.credentials.json`、`~/.claude.json` 里的账号、`~/.codex/auth.json` 或 Codex 的钥匙串项、Copilot 的、Cursor 的、Devin 的、Kiro 的、Gemini 的、ZCode 的、Command Code 的、OpenCode 的 `auth.json`），不读任何钥匙串或 Secret Service 项（`security`、`secret-tool`），也不问任何 agent CLI 谁签入了。所以也没有哪道关卡需要被问「发现被关掉了吗」——这道关卡整个被删掉了，而不是被默认打开。订阅照旧被服务，API key 的 provider、中间件 plugin 和 Pi 扩展也照旧。星鸣自己留下的东西（`logins.json`、`plugin-auth.json`、`migrations.json`）保持原样：它们装的是星鸣自己签入的账号和 plugin 的登录态，不是从别家工具读来的。

一个已登录账号的模型列表只存在于它的厂商那里（Codex 登录对应 ChatGPT 后端的 `/models`，等等），所以 `FetchNew` 去问那些还没取到的列表。每个前端在启动时都会调它：窗口（`startBackend`，然后在 `/api/state` 后面跑 `FetchNewSoon`）、TUI（`Init` 里的 `fetchModelsCmd`）和 `starling serve`（#1789，reyoung：终端和无头的网关一直只提供内置 Cursor 的兜底 `auto`，直到那个列表被手工取回来）。列出账号时不再问任何 CLI 谁签入了，所以一次查看不用等 `firstAsk`（3s）。它报告是否有账号没拿到自己的列表（失败，或者失败后等着 `newFetchRetry`）：TUI 于是过一分钟再问一次（`modelsRetry`），`serve` 也照样循环，窗口则从自己的页面再问。列表到达时正开着的 TUI 模型选择器会被就地填上（`relist`），保留它的过滤条件和光标下的那个模型。`TestFetchNewAccount` 和 TUI 的 `TestTUIFetchesSubscriptionModels`／`TestTUIAsksAgainForAMissingList` 覆盖了它。

## 运行时路径

<a id="runtime-path"></a>

1. **添加。** 供应商页面通过 `Add` 或 `Save` 添加一个带 key 的 provider，或者通过 `StartSignIn` 添加一个账号。星鸣自己签入的账号由 `Accounts` 列出，用户不需要任何一步；别家 agent 自己的登录态一概不被读。
2. **解析。** 网关用模型名调用 `provider.Resolve` 或 `GroupFor`，然后在那个 provider 的 key 或账号上规划候选。
3. **签名。** 每一次尝试，`Sign` 都会给请求配上它的 auth。一个快要到期的令牌会先被刷新，轮换后的令牌回到它们唯一的主人那里：`logins.json`；账号被切给 agent 之后，agent 自己的存放处里也是同一份。
4. **额度。** 用量端点有速率限制，所以 `SubscriptionUsage` 会缓存它的结果：缓存的那份立刻返回，过期的那份在后台刷新。当一个账号的窗口重新开始时，`OnRenewed` 会告诉网关，好让一个歇着的账号能回来：一个被花掉的 Codex 重置（`renewedNow`），或者一次路由采用的读取（`Allowances`，agent 是这个账号的用量被读取时所挂的那个，`claude` 或 `plugin:<id>`）发现这个账号满到了比上一次更早（`renewedFrom`，key 的读取按它判断）：整个账号，或者某些模型的一个池子，而整个账号的窗口都盖在它上面。一个按它的路由用到低于 `SpentShareOf` 的窗口，或者一个重置已经过去的窗口，就不再是满的；一个满了但重置时间不明的窗口，就永远是满的。一个 Claude 账号只要有一次新的 `/usage` 或者重置过去显示出它耗尽的那个窗口又开始了，就回来了，而不是等 Claude Code 的拒绝里说的那个时间；它那个用完的周里的五小时又开始了，什么也说明不了。一次首次读取、一次失败的读取、一次同样的读取，或者一次把满的窗口排除在外面的读取，都说明不了什么，而一个被花掉的重置只会被说一次，由 `renewedNow` 说。一次 key 的读取如果发现一个它原本是满的窗口（按它的路由算 `SpentShareOf`）不再满，或者满到更早，也会说明这一点，agent 是 `""`，用的是那个 key 的 `KeyAllowanceID`，所以一个超出上限的 key 在上限被提高或用量被重置之后就回来了；一次首次读取、一次失败的读取，或者一次发现它更满的读取，说明不了什么。一个因为配额被拒的账号，在下一次问的时候，它的 agent 的额度会被再读一次（`StaleAllowance`）。一次在那之前就已经失效的读取：它读到的被保留为「未读」，所以它之后落下的那次问会再读一遍，key 则由 `StaleKeyAllowance` 这么做。

一个 provider 取回来的模型列表保留上游的 id 和顺序。显示名优先用 `starling_label`，然后是 `display_name`，然后是一个没有厂商式 `: ` 前缀的 `name`，最后是 id（[`live.go`](../../internal/catalog/live.go) 里的 `fetchOne`）。OpenRouter 那种带前缀的 `name` 交给目录处理。`Decorate` 和 [`Named`](../../internal/catalog/catalog.go) 用目录补上缺失的名字，当一个建议的名字会和列表里另一个模型撞上时保留 id，包括两个 id 只在大小写上不同的情况。供应商给出的、已被接受的名字按给的保留。用户挑了、而上游没有列出的模型，会对着所有列出的名字和 id 命名；列出的模型保留它们 `Available` 的名字不变（[`Exposed`](../../internal/provider/models.go)）。

## 约束与失败行为

<a id="constraints-and-failure-behavior"></a>

一个有意不去要的额度（一张卡片刷新范围之外的已存 Claude 账号，或者额度被设成 *当我问的时候*）可以用上一次的读取，并带上 `readDeferred: true`。`AsOf` 和 `ReadAt` 仍然给那个快照标日期；GUI 会说它这次没有被刷新，而不是说某个请求失败了。网络失败、`/usage` 不可用和账号的拒绝都不算延后的读取。这个标记也会传到 `starling quota --json` 和网关报告里。见 [`quota_last.go`](../../internal/provider/quota_last.go) 和 `TestQuotaDeferredReadIsNotFailure`。

额度的读取按 provider、小写的账号和窗口存在 `quota-history.json` 里（[`quota_history.go`](../../internal/provider/quota_history.go)），最多保留 45 天、每个窗口 6000 个点。失败或过期的读取什么都不加。`newCycle` 在上一次的截止时间过去、出现或消失、往回退超过五分钟、或者往前跳超过经过的采样时间再加五分钟时保留一个边界。补给超过五个百分点、而截止时间在五分钟内没变的，也算一个边界：一次手动或厂商的重置不必改截止时间。更小的修正，以及随时间往前推的滚动截止时间，不会把这个窗口分开。这些是观察到的边界，不是「谁重置的」记录；两次读取之间的多次重置，以及被后续花费掩盖掉的补给，都恢复不出来。采样压缩和同步合并会把读数保留在检测到的边界两边。

整个窗口的估计在 [`window_holds.go`](../../internal/usage/window_holds.go) 里会排除那些调用落在该账号某次「干跑」里的窗口，因为在那里被回答的调用可能是用额度或额外用量付的（#2010，NorethSea）。一次已知的厂商重置会结束一次干跑，即使下一次轮询更晚才看到那次补给，而随后的干跑不会早于那次重置开始，所以两者之间的调用仍然算。一次重置时间不明的干跑会一直开着。一次在它自己重置之后取的过期干跑读数不能延长一次干跑。额度余额是按整个账号读的，显示时四舍五入，而账本里没有逐请求的额度扣减。比较两个余额无法判断是哪一次并发或外部的调用花掉了额度，所以不做逐次归因。一次晚于「重置减去跨度」被观察到的补给（`QuotaPoint.StartsCycleAfter`，和历史采样保留的是同一批边界）会开始被推算的周期，所以固定截止时间的补给之前的调用仍留在它之前那个周期里。卡片的窗口保留自己的跨度，所以它的节奏是厂商的（`withSpansOf`）。一次没有记录到起点的首次读取不是一次重置。`HistoricalWindowHolds`（[`window_holds_history.go`](../../internal/usage/window_holds_history.go)）以同样的方式推算过去某个周期的窗口，每个窗口按它在那个区间里自己的最后一次读取，用那次读取的百分比和边界、缓存卡片的模型范围，以及只在那次读取之前的调用和读取。一个实时被关住的卡片（一个余额、一个远端、一个错误）对过去的周期同样被关住，而缓存卡片上已经没有的窗口被排除在外。过去的价格不留存，所以成本按今天的 API 列表价算。见 `TestWindowHoldsDryAgainAfterReset`、`TestWindowHoldsUsesObservedRefillStart` 和 `TestHistoricalWindowHoldsUsesEachWindowsOwnReading`。

- 一次成功的 Codex 额度重置会让一个账号正在进行的读取作废，即使那次读取和那次重置带着同一个时钟时间戳。`Allowances` 在它的锁下给 `usedCache.generation` 拍了个快照，而 `forgetAllowance` 会为那个账号推进这个代号；重置之前的读取会在路由能用它之前被丢掉。见 [`routing.go`](../../internal/provider/routing.go) 和 `TestResetAllowanceKnownAtOnce`。
- 每个刷新令牌只有一个主人。厂商在刷新时轮换令牌，所以一个令牌的两份副本会把彼此签出。`savedTokenMu` 阻止两个请求同时刷新同一个已存账号。
- 一个 Claude 订阅账号只用于 Claude Code，且只通过真正的 Claude Code 可执行文件。
- Claude 的用量读取按 `claudeAskGeneration` 排序，而不是按墙上时钟。`AskClaudeUsage` 和一张 Claude 卡片的 `RefreshUsage` 在先持有订阅缓存、再持有登录缓存锁的情况下推进它（`markClaudeUsageAsked`）。每个缓存在发起一次读取前在自己的锁下记下它，在发布时也在那个锁下检查它：更新的一次问会阻止 `LoginUsage` 保留更旧的那次读取，也会让 `SubscriptionUsage` 保持到期、需要再读一次。每个 `claudeWindows` 条目记下它那一轮回答时的代号。时间戳的零值哨兵、`tried`/`wait`、30 秒的下限、空闲行为和已存账号的范围都不变。见 [`login_usage.go`](../../internal/provider/login_usage.go)、[`subscription_usage.go`](../../internal/provider/subscription_usage.go)、[`quota_refresh.go`](../../internal/provider/quota_refresh.go)。
- 一个已存 Claude 账号的额度只会在它自己的卡片被刷新时才读（#1630；`savedRefresh`：为那个账号的 `RefreshUsage`，所以 `cardRefresh.wants` 会要它，而这次读取会被问出来）。真正的 Claude Code 在 `CLAUDE_CONFIG_DIR` 指向那个账号的 `claudeSavedDir` 时跑 `/usage`（`readSavedClaudeUsage`，通过网关的 `claudeUsage`），所以星鸣从不带着令牌自己去调 Anthropic，而 Claude Code 所签入的那个账号也不会被切换。用量页被打开、`starling quota` 和 `starling accounts` 都会问每一张卡片，所以不会启动任何一个已存账号的 Claude Code：它们保留它上一次的读取，在有过一次之前则是 `errClaudeSaved`。后台读取保留上一次的读取，30 秒的按账号下限对重复刷新照样成立。Claude Code 在它运行时可能会在那个目录里刷新账号的令牌（它自己的锁文件让同一个目录里的两个 Claude Code 不会同时刷新）。所以 `inSavedClaudeDir` 在它运行时为读取占着 `claudeDirRun(user)`，而 `switchSavedLogin` 要写时先取它，运行结束后 `syncSavedClaude` 在 `savedTokenMu` 和 `loginsMu` 下把一次轮换过的登录复制回 `logins.json`。一个已存账号的预热同样这样跑。见 [`claude_usage_saved_test.go`](../../internal/provider/claude_usage_saved_test.go)，它覆盖了刷新、别的账号被放着不动、下限、后台读取、一次等待运行的切换，以及被保留的轮换后的登录；`TestClaudeUsageRunsInSavedAccountDirectory` 检查命令运行的目录。
- Claude Code 的 `/usage` 在重置落在今年时打印一个不带年份的重置（"Oct 9, 2:59pm (UTC)"），在更老的版本里则只打印一个时间（"3pm"）。`claudeResetTime` 把它读成它那个窗口的结束，所以绝不超过窗口的长度（会话是 5 小时，一周是 7 天），再加上 `claudeResetSlack`：一个日期是在去年、今年和明年里第一个「不足一天且不更靠前」的那个，只有一个时间则是下一个不更靠前的那个。哪里都没有时，比如一份已经过了好几天的读取，它取最近一个已经过去的，所以那个窗口读起来是续期了，而不是满了一年。时钟回拨、同一个时间出现两次时，取还没过去的那个读取。一周的那个只带时间的值，在它刚重置之后读到时，仍然读起来是明天的。
- 一个 Copilot 账号由它的 GitHub 登录名和主机来认（`CopilotAccountName`，#1220）：github.com 上的 `mona`，企业版的 GHE.com 上的 `mona@acme.ghe.com`。那个名字是它 `logins.json` 里的 user、它在每个列表里的那一行、它的用量卡和它的逐账号路由设置，也是 `SwitchLogin`、`SetLoginOn` 和 `ForgetLogin` 接受的东西，所以两个主机上的同一个登录是两个账号，彼此不会互相覆盖，也不会被当成别处的账号而丢掉。一个早先在企业版主机上只按登录名存下的账号，会按带主机的名字被读（`copilotSavedName`），保留它的 id；被记住的旧账号也是这样被就地改名的，如果它本来是隐藏的就仍然隐藏（`copilotRenamed`）。两种改名都会在新名字写进 `logins.json` 之前，把该账号在 `providers.json` 里的逐账号设置（代理、模型、上限、并发）从光秃秃的登录名搬到新名字下（`renameSettled`）：新名字已经有的设置保留，而在 `providers.json` 读不了或写不了期间，那个账号仍按旧名字保存，它的设置也跟着。`starling accounts switch|forget copilot` 接受完整的名字、带 `--host <name>.ghe.com` 的登录名，或者在它只指向一个账号时的登录名本身。
- 一个 Codex 账号由它的邮箱来认，带上一个工作区席位的套餐（`codexUser`），而同一个邮箱在另一个工作区里的第二个席位则用那个名字后面跟上工作区来认（`codexName`）：`me@example.com · Team · ws-two`。Codex 所签入的那个账号到处都按它被保存时用的名字（`codexLiveName`）：它 provider 的 `Account.User`（`codexAccount`）、`liveLogin`，以及它的 session 身份（`SessionIdentities`）。它的额度、占用与固定（`restKey`）、上限、代理、模型列表、一个网关 key 的账号列表（`LoginID`）和 Routing 页面都按那个名字，所以同一个邮箱的两个席位绝不会被读成一个（#1424）。
- 发往 ChatGPT 后端（`CodexBase` 的主机）的每个请求都走 HTTP/1.1，就像 Codex 自己和它说话那样：[`netproxy.Dispatch`](../../internal/netproxy/netproxy.go) 建的每个传输（`http.DefaultClient` 的、网关的）都会把 `netproxy.HTTP1` 点名的请求通过一份自身的 HTTP/1.1 副本发出去，那份副本的 TLS hello 不提供 h2，而 provider 包把 `HTTP1` 设成 `codexBackend`（[codex_http1.go](../../internal/provider/codex_http1.go)）。这覆盖了网关的每一轮、模型列表、预热、额度、它的重置以及花掉一次重置，全都走当时生效的代理，账号自己的也在内。其它每个厂商仍然被提供 HTTP/2。
- 用户添加的 provider 可以选择不检查它的证书（`InsecureTLS`，编辑器的 Certificate 行，#2383：局域网里的 vLLM、自签证书后面的 Ollama、一家公司自己的 CA）。只有 base URL 是用户自己的那个才吃这一套（`TakesInsecureTLS`：不是账号、没有预设、不是 Vertex、不是某个订阅或 plugin 的 id）；别的情况下 `Save` 会拒绝它，而手工写进 providers.json 的一个会被忽略。`Provider.Via` 随后会加上 `netproxy.WithUncheckedTLS`，带上它自己 base URL 的那些主机（`UncheckedHosts`：Chat、Responses、Anthropic、Gemini、Decide），所以通过一个 `Dispatch` 传输代它发出的每个请求（网关的每一轮、count_tokens、模型、测试和探测、余额）只对那些主机跳过检查，而且每个都在一份分开的传输上（`route.unchecked`）。一个重定向，或者另一个主机上的模型、余额或图像 URL，仍然会被检查，而 `netproxy.With` 会把那个许可从为别的 provider 发的请求上撤掉。一个 `https://` 的代理会用同样的 TLS 配置去拨，所以它的证书也会不被检查：这样的请求被拒绝（`ErrUncheckedOverHTTPSProxy`）；`http://` 或 `socks5://` 的代理则照用。备份、导出和同步会带着这个字段和 provider 一起走；导入链接不会。
- 星鸣签入的 Copilot 账号由 `copilotLogin` 读出（[account.go](../../internal/provider/account.go)）：编辑器或 Copilot CLI 自己留在 `~/.config/github-copilot/apps.json` 或 `hosts.json` 里的登录态一概不被读，也不问任何 CLI 谁签入了，所以这个账号只可能是星鸣自己用设备码流程签入的那一个。GitHub 拒绝把那个令牌换成 session 令牌时（401 或 403，`copilotRefusals`，一小时后再试一次），那个账号的登录态就被记为失效，错误会让人重新在星鸣里登录。
- 星鸣不读任何别家工具的钥匙串项，所以「一次可能弹过窗的读取被拒绝后十分钟内不再问」这一整套退避（`keychainDeniedTTL`、Copilot 的 `copilotCLISecret`、Cursor 的 `cursorKeychainToken`、Claude Code 的 `readClaudeKeychainItem`）随读取别家登录态那一层一起移除了（#2408）。星鸣只往 Codex 的存放处写自己那个登录，写的是它自己的 OAuth 流程拿到的凭据，见 [`codex_store_write.go`](../../internal/provider/codex_store_write.go)。
- 一个读不出来的 `providers.json` 是一个错误，绝不是一个空列表。在一个空列表上保存会把每个 provider 都丢掉。
- 当 `logins.json` 无法被解码成已存账号时，读取保留之前读到的账号。在保存一次改动之前，`lastgood.Keep`（[lastgood.go](../../internal/lastgood/lastgood.go)）会把当下那个文件留一份：读得动时留成 `logins.json.bak`，也就是它最后一个完好的世代；读不动时则另存为 `logins.json.bad-<time>`（同一秒内的另一个是 `-2`、`-3`……），包括账号字段类型不对但 JSON 有效的情况，这样它的凭据还能被找回。如果已有的文件读不了或者拷贝失败，保存会返回那个错误，原文件保持不变。文件不存在时照常新建。
- 一台写到一半就掉电的 Windows 机器会把 `logins.json` 和 `plugin-auth.json` 留在全长的状态，每一个字节都是零（#1505）：改名在数据之前到了磁盘。星鸣自己状态的每一次写都走 `steady.WriteFile`（或者 `edit.WriteAtomic`），后者在把它改名进去之前先把临时文件刷盘，plugin host 的 `writeDurable` 也一样。agent 自己登录态的每一次写也一样（#2239）：`codexToken` 轮换后的令牌写进 Codex 的 `auth.json`（`~/.codex`，或者设了 `$CODEX_HOME` 时用它；Codex 把登录态放在那里时则写它的钥匙串项），以及 `writeClaudeCredential` 的 `.credentials.json`，都走 `writePrivate`，绝不用会截断的 `os.WriteFile`，所以一台写到一半掉电的机器会把旧的登录态完整留下，而在 Windows 上，一个被别的程序短暂占着的文件会被等过去（`steady.Rename`），而不是在磁盘上的刷新令牌已经被花掉时把轮换丢掉。一个存在但在冷启动时读不出来的文件，会从它的 `.bak` 读（`lastgood.Read`/`Fallback`）：`logins.json`、`providers.json`、`migrations.json`、`settings.json`、`profiles.json`、`plugins.json`、`plugin-auth.json` 和 `mcp-signins.json`。`caller-keys.json` 用同样的方式刷盘，但绝不从 `.bak` 读：上一次写里被吊销的 key 会回来，所以一个不读它的存储仍然拒绝每一个 key。恢复的动作会被记日志，并列在 `/api/state` 的 `recovered` 里，窗口会把它说一次（`recoveredOnce`）。`.bak` 故意比最后一次写落后一个世代：一次崩溃会把最新的一次写清零，所以用它做的副本也可能被清零。没有一个好的 `.bak` 时，那个文件是未知的，绝不是空的：一次登出会让 `plugin-auth.json` 或 `mcp-signins.json` 保持原样（星鸣自己的那个会返回错误），而一次加上的登录会在写之前先把文件另存一份。
- 一个状态文件的读取者如果把读不懂自己类型的那个当成空的，那么在它被覆盖之前会先被另存一份（`lastgood.KeepUnparsed` 配合 `lastgood.Into[T]`，#2263）：形状不对但有效的 JSON、给 map 的 `[]`，都算作读不懂。拷贝不出来就停止写。这些是 `stash.json`、`applied.json`、`wsl.json` 和 Codex 的 `starling-models.json`（[agent](../../internal/agent/)，文件读不懂时它手工加的模型 key `codexcat.Keep` 保不住）、`sessions-wsl.json` 和 `gateway-sessions-hidden.json`（[sessions](../../internal/sessions/)）、`stepfun-auth.json`、`login-returns.json`、`quota-history.json`、`balance-history.json` 和 `credits-daily.json`（[provider](../../internal/provider/)）、`claude-desktop.tiers.json`、`plugin-updates.json`、`usage-computer.json` 和 `sync-state.json`。一个每日签到的文件（`workbuddy-checkin.json`、`trae-checkin.json`、`minimax-checkin.json`、`qoder-checkin.json`、`plugin-checkin.json`）存在却读不了、或者解析不出条目时，是未知的（[`workbuddy_checkin.go`](../../internal/provider/workbuddy_checkin.go) 里的 `readCheckins`）：它厂商的签到既不问也不写，所以没有账号一天被签到两次，也没有条目丢失，文件保持原样，每个账号的结果是 `failed` 并带上原因（那个循环 30 分钟后再试一次，手动按一下会说为什么），而卡片显示的是这个进程里最后从它读到的东西。文件不在时是空的。`TestCheckinUnreadableFileLeftAlone` 覆盖了它。星鸣自己能重新填上的那些缓存（最后的额度读取、预热标记、plugin 图标、npm 和 GitHub 的查询、客户端形状、席位、告警标记、`served.json`、`bun/state.json`）仍然会被覆盖写：丢掉一个的代价是一次重新取，或者一次重复的提示。
- 网关和一个从终端跑起来的星鸣会改同一批文件（#1674）。`loginsMu` 是一个 [`filelock.Mutex`](../../internal/filelock/filelock.go)：除了互斥锁，它还在 `logins.json.lock` 上持有一个 OS 锁（flock，Windows 上是 `LockFileEx`），而拿到它会让 `logins.json` 被重新读一遍（`filememo.Look`），所以每一次作为改动依据的读取都看得见另一个星鸣写了什么，而网关写的那个刷新不会被回写覆盖。`savedTokenMu` 以同样的方式持着 `logins.json.renew.lock`，所以两个星鸣绝不会花掉同一个刷新令牌。`caller-keys.json`（`access`）和 `mcp-signins.json`（`mcpauth`，续期时外面套着 `mcp-signins.json.renew.lock`）也是在这样的锁下被改的；`plugin-auth.json` 本来就是，在 `plugin-auth.json.lock` 下，`host.js` 也拿它。另一个星鸣持有的锁会被等最多 `filelock.Wait`（10 秒），然后不等了就继续走，就像以前只有一个时那样。`rememberLogins` 在只有 `Seen` 会往前走、而存下的那一个还不到 `seenEvery`（10 分钟）新时什么都不写，所以一次只列账号的运行（`starling ls`、`providers`、`sessions`、`usage`）会让 `logins.json` 保持原样。见 [`logins_lock_test.go`](../../internal/provider/logins_lock_test.go)，它覆盖了这两个，第二个是在另一个测试进程于这一次读写之间写入的情况下。
- Codex 或 Claude Code 所签入的那个账号可以被暂停（`SetLoginOn` 关掉，#263），但只在它的另一个账号开着的时候可以。网关于是什么都不发给它：Codex 自己模型的每一轮都走路由，而路由会跳过它（`OwnPaused`）；一次原生压缩（`/responses/compact`）会走第一个没在歇的、开着的那一个账号，并以那个账号的签名发出（[`codex_backend.go`](../../internal/gateway/codex_backend.go) 里的 `compactOn`）。最后一个别的账号被关掉时，被暂停的那个又被用上。一个被关掉的 Codex provider 不是暂停：Codex 自己模型的请求仍然按原样在它自己的登录态上中继。
- 一个被关掉的 provider（`Off`，#163）仍然保存着。网关会说它被关掉了，而不是说这个模型未知。
- 一个被关掉的订阅（`Off`），或者它的账号被星鸣移除（`Hidden`），在后台被放着不管（[`left_alone.go`](../../internal/provider/left_alone.go) 里的 `leftAlone`；Riko 报告，他的 Claude 被关掉后仍然每分钟跑一次 `claude auth status --json`）。现在没有任何 CLI 会被问谁签入了：它上次说过什么（记在内存或 `cli-identity.json` 里）就会被端上来，所以那个账号仍然列着，可以再打开。它的额度同样不被读（`fetchSubscriptionUsage`、`loginUsageAt`），一个已存的 ChatGPT 登录不被续期（`RenewLogins`），agent 的账号不被切换（`NextLogin`），一个窗口不被预热（`keepWarm`），它的模型列表不被取（`newDue`），循环也不做每日签到（`checkinNow` 且 `soon` 为 false；手动按一下仍然会签到），一个快要用完的 Codex 重置也不被读和花掉（`SpendExpiringCodexResets`，#2226；`TestExpiringResetLeftAlone`）。plugin 的模型列表（`KeepPluginsListed`）是一次性向 plugin host 问的，不会按 provider 拦下。
- 一个被移除或被关掉的 provider 会把它的模型从目录里拿掉。[Agent 接线](agent-wiring.md)里的 `Reseat` 把 agent 从它们身上挪开。
- 一个标了 `NoList` 的预设用它自己的预设模型列表，而不去请求 `/models`，并且忽略之前取到的列表，包括它们的协议和 key 限制，除非用户设了 `ModelsURL` 或者挑了一个标着 `Lists` 的区域。每个区域可以带一份不同的列表。Volcengine Ark 的 Coding Plan 和 Agent Plan 各用各自的预设列表。两个计划都把它们的 embedding 模型单独列出来，不与 agent 的对话模型列表混在一起；Agent Plan 还把自己的图像和视频生成模型暴露给设置 → 图像；Ark 本身在小号和中号 Agent Plan 上拒绝视频生成，那两个档位只有大号和最高档才有。星鸣还不会服务的模型（Agent Plan 的语音模型）不被宣传。Ark 的按量付费区域仍然取自己的列表。Coding 的 `/api/coding/v3/models` 返回的是一份通用的 Ark 目录，而不是那个计划的模型 id，而 Agent 的 `/api/plan/v3/models` 返回 404。[`presets.go`](../../internal/provider/presets.go) 定义了这些选择；[`models.go`](../../internal/provider/models.go) 里的 `List`、`fetch`、`live`、`planModels`、`PlanEmbeddings`、`PlanDrawers` 和 `PlanVideos` 在添加、刷新和读缓存模型时套用它们。`TestVolcengineModelLists` 检查这些计划不发出列表请求、忽略旧的缓存列表并返回自己的预设模型；按量付费和显式的列表 URL 仍然会发请求。
- 一个被限在某些账号上的网关 key（#905），限的是它的列表所点名的那些 provider 的账号：它没点名任何账号的 provider，key 的用法和从前一样。key 的菜单在这样一个 provider 的每个账号上都会这么说（"Used: no … account is picked"），而它的徽标的提示会说，一个 key 因为它的模型被挡在某个 provider 之外（#2077：把所有 Codex 账号都取消勾选，Codex 的模型仍然被服务）。那份列表按账号的稳定 id 保存它——`logins.json` 里的 `id`，写入时定下、改名时保留；不保存登录态的那些 agent（以及 plugin）按账号名字的哈希来认，所以在那边被改了名的账号会从某个 key 的列表里掉出去，让它收得更紧，绝不会更宽。给每个 agent 都存一个 id 是更大的改动，不是这一次的。
- 一个 sub2api key 的窗口是固定的：每个从它空着之后这个 key 的第一次请求开始，与中继的一天对齐，而一个还没开始的窗口说 `used 0` 且没有 `reset_at`，所以它被当作从现在起续一个跨度。它们只算这个 key 的花费，不算它背后那个中继的账号。`ForgetBalances`（一个 key 或余额 URL 变了）会让每个 key 的窗口在下一次被问时重新读一遍，在那之前开始的一次读被丢掉；在那之前，上一次的读取站得住，比卡片上的还新，而路由的读取从不写它。换过的 key 是另一个 key（`keyID`），有它自己的窗口。
- 一个 Volcengine Ark provider 的 access key（`TakesVolcAccessKey`：它的任何 base 在 `ark.<region>.volces.com` 上）跟它的 key 放在一起，而且绝不发给 GUI：`/api/providers` 告诉编辑器它的 ID，以及有没有存下 Secret（`accessKey`）。一次把 Secret 留空的保存会保留它，一次把 ID 漏掉或发空的保存会两者都保留（在 key 给出之前就打开的编辑器会发 `""`，#1821），而 `clearAccessKey` 两个都丢掉。ID 和 Secret 在 key 去的所有地方都一起走：一次拷贝会带走它们，即使它的表单发的是源头的 ID 而没有 Secret（`AddCopy`）；一次不带 key 的备份或同步两个都没有（`withoutKeys`）；而一次还原、镜像或同步会保留这台机器的（`Restore`、`Mirror` 和 davsync 的 `take` 里的 `KeepSecrets`），当它来的时候不带 key，或者带着同一个 key 且完全没有 access key，就像 v0.1.1142 之前的星鸣、或者一个从未被给过 access key 的那样发来（#1821）；另一个 key 是另一个账号，会带自己的来。一次不带 key 的拷贝也以同样的方式保留这台机器的 secret 头（`SecretHeader`）。一个没有 provider 持有那个 access key 的计划端点，会得到一张说明该给哪一张的卡片（`accessKeyCard`、`needsAccessKey`），带一个通往那个 provider 设置的按钮，而不是被排除在外。一份带 UTF-8 BOM 保存的 `providers.json` 会穿过它被读，而不是被当成一个坏了的、由它的 `.bak` 顶替的文件。计划的读取取决于端点：`/api/coding` 问 `GetCodingPlanUsage`，`/api/plan` 问 `GetAFPUsage`，按量付费（`/api/v3`）没有卡片；区域由主机决定。每个 access key 和计划读一张卡片。`GetCodingPlanUsage` 的回答（`QuotaUsage[]`，带 `Level`、`Percent` 和以秒计的 `ResetTimestamp`）是建在它之上的三个工具所读的那一个；`GetAFPUsage` 的各个桶则按那些工具读的每种形式来读（`Quota` 或 `Total` 的 `Used`，或者 `Percent`；`ResetTime` 或 `ResetTimestamp`），这里没有一个是从真实账号上看到的。一个这些都不读的回答会在卡片上说明，并用回答的开头。改动 access key 会丢掉缓存的卡片（`ForgetPlanQuotas`）。
- 一个 Tencent Cloud provider 的 SecretId 和 SecretKey 以同样的方式被保留、列出和保存，存放在同样的字段里（`AccessKeyVendor` 告诉编辑器它们是谁的：`accessKey.vendor`，预设的 `accessKeyVendor`）。只有 Token Plan 企业版的端点会用它们来读（`TakesTencentAccessKey`：`tokenhub.tencentmaas.com` 上的 `/plan`，区域 `ap-guangzhou`；或者 `tokenhub-intl.tencentmaas.com`，`ap-singapore`）；个人版套餐（`api.lkeap.cloud.tencent.com`）没有用量 API，TokenHub 的按量付费也没有套餐，所以两者都没有卡片。预设列出它那些接受它们的区域（`accessKeyRegions`、`presetAccessKey`），而编辑器只在那些区域显示 SecretId 和 SecretKey。`DescribeTokenPlanList` 给出该账号的团队套餐（一个子用户只看得到它自己建的那些）；每个套餐都被问一次 `DescribeTokenPlan` 以取它的 `PackageInfo` 和 `TokenSummary`，列表则保留回答里没有的那部分。卡片上那一个窗口是 `CycleQuota` 的 `TotalUsed`（否则是 `TotalQuota`），在 `TokenSummary.CycleEndTime` 重置，否则从 `StartTime` 起按月算，且绝不超过 `ExpireTime`。一个不是 `enable` 的套餐会在套餐名字旁边说它的状态。错误以 200 回来，带着 `Response.Error`；一个 `AuthFailure…` 或 `UnauthorizedOperation` 的错误会让人去检查 key。它是照着 API 文档（api/1823/132270 及同类）和签名文档里的示例建起来的；这里没有一个是从真实账号上看到的。
- 一个 Codex 账号是否花掉它的额度（设置里的 `CodexNoCredits`，选择退出，按小写的邮箱）只影响网关的路由。它绝不影响 Codex 签入的是哪个账号：`NextLogin` 在它路由的已花份额（最多 100%，不管花的是额度还是不是）上从一个账号移开。
- 一个 Vertex AI provider 的凭据只在一个请求被签名时才读（`Sign`），所以添加、列出和显示它都不会问 Google 任何事。没有给出 `credentials`、也没有一个 Application Default Credentials 被查找的所在位置的文件时，请求会以 `no Google credentials at <file>` 失败，并点名 `gcloud auth application-default login` 和这个 provider 的凭据文件是给它凭据的办法。一个不在那里的 `credentials` 文件以同样的话失败，并让人去纠正它或清掉它。当 Google 拒绝了某个人的登录（被撤销，或者超出了该组织的会话时长）时，错误会说明怎样为所用的文件重新登录（`signInAgain`）：gcloud 的 Application Default Credentials 用 `gcloud auth application-default login`，文件模拟某个账号时再加上 `--impersonate-service-account=<account>`；gcloud 的 `legacy_credentials/<account>/` 下的文件用 `gcloud auth login <account>`；别的文件就重写一遍，或者给 provider 另一个。新的文件在下一次请求时被读，不需要重启。
- Vertex AI 不读这些：Compute Engine、Cloud Run 和 GKE 的元数据服务器；工作负载身份联合（`external_account`、`external_account_authorized_user`，按名字拒绝）；`universe_domain` 不是 `googleapis.com` 的凭据；Vertex AI 的 express 模式 API key（保存时拒绝 key）。不发配额项目：Vertex AI 按 URL 里的那个项目计费。
- `GOOGLE_APPLICATION_CREDENTIALS` 和 `CLOUDSDK_CONFIG` 在 `agentenv.Vars` 里。桌面 app 在启动时没有带着它们，就从登录 shell 取（`proc.UserPath`，macOS 和 Linux），而 `testenv` 把两者都清掉。Vertex AI 按它们被设置的样子来读（`vertexEnvPath`），不通过 `appdir.Getenv`，后者把一个相对的值当作没设置：以 `~/` 开头的那个是家目录，而仍然不是完整路径的那个会被拒绝，并点名那个变量。被略过的话，请求就会用 gcloud 自己的文件签名，而那可能是另一个账号的（某个人的，在那个变量点名了一个服务账号的 key 的场合）。
- Vertex AI 预设的 `HeaderHints` 是 Google 的 Priority PayGo 和 Flex PayGo 头，`X-Vertex-AI-LLM-Request-Type` 和 `X-Vertex-AI-LLM-Shared-Request-Type`：编辑器会提供把它们加上，值是用户的，它们按 `Headers` 的方式发出去。Priority PayGo 没能确认：在试它的那个项目上，Vertex AI 回答的 `trafficType` 是 `ON_DEMAND`。
- 每个账号都留着一条用量上限（`AccountCaps`，1–99），在它旁边每个窗口也有一条（`AccountWindowCaps`，按账号和窗口的 `capId`，也就是它名字的小写形式：`WindowCapID`）。一个窗口自己的份额压过账号的；100 表示那个窗口没有上限。`CapsOf` 给出两者（`WindowCaps`），`CapHeld` 和 `capReached` 按每个窗口自己的份额判断，而 `SetWindowCap`（GUI `provider/windowcap`、`starling provider account-cap <id> <account> --window <name>`）设置一条。没有窗口上限的配置按原样读。
- 一个重置时间已经过去的窗口又开始了，不管它被读到时是多少份额（`resetPassed`）。这既对一份保留着的旧读取（`AsOf`）成立，也对一次新鲜的读取成立：Claude Code 的 `/usage` 给出的重置精确到分钟，而且可能滞后，所以刚重置之后的一次运行仍然可能说 100%，并带着那个重置。`claudeWindows` 在每条路径上都会把这样一个窗口空着交回来，而 `usedPast`、`usedUp`、`BackAt` 和 `capReached` 在判定一个账号用尽时把它排除在外，对 Codex、Claude Code 和 `starling quota wait` 都一样。一张卡片仍然可以显示一份保留着的读取，按它被读到时的样子（`reported`，用于 `/usage` 不可用时的 Claude 卡片）；那改变的是它显示什么，而绝不是用哪个账号。一个 `/usage` 只带时间给出的重置（"resets 3pm"）可以被读成它的下一个，也就是往后一天（`claudeResetTime`），而在这里就不再被看作已经过去。
