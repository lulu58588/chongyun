# 网关路由与故障转移

<a id="gateway-routing-and-fallback"></a>

网关是崇云科技的本地 LLM 端点（默认 `127.0.0.1:3425`）。它提供 Chat Completions、Responses、Anthropic Messages 和 Gemini。它为每个请求找出对应的 provider、key 或账户以及模型。当上游不讲 agent 用的 API 时，网关做翻译。当上游在回复的任何部分发出之前失败时，网关换到下一个候选。

本页讲的是请求如何被路由。改变请求和回复的 plugin 在[网关 middleware](gateway-middleware.md)里。由 plugin 提供的订阅在[provider 与 plugin 归属](provider-plugins.md)里。

WorkBuddy 和 CodeBuddy Code 的 `X-Conversation-ID` 是 `sessionHeaders` 里的一个原生 session 头（[`gateway.go`](../../internal/gateway/gateway.go) 里的 `sessionOf`、`nativeSessionOf`、`conversationID`）。即使两个对话的第一条消息相同，它也让这两个请求彼此分开。同一个身份用于 affinity、用量和 Routing 页面，转发给远端崇云科技时会被保留，但不会复制给普通厂商。既有的头优先级不变。此前按推断出的首条消息摘要保存的 affinity 不会迁移到新识别出的原生 id 上，所以升级之后的第一个请求可能重新挑一个账户。历史用量不会回填；见[网关 session 聚合](gateway-sessions.md)。

## Codex 标题、描述与预测

<a id="codex-titles-descriptions-and-predictions"></a>

Codex 的标题和描述请求是各自独立的隐藏轮。设置 `CodexTitles` 和 `CodexDescriptions` 分别挑各自的模型；一个空设置保留所请求的模型。在一个崇云科技的模型上，两条路径都把普通的模型文本包进 Codex 要求的那个对象里。标题用 `{"title": ...}`；描述用 `{"description": ...}`，带非空的文本，不编造最大长度。标题 Off 模式不会关掉描述。

[`codex_titles.go`](../../internal/gateway/codex_titles.go) 里的 `codexTitlesTo`、`codexDescriptionsTo`、`codexTitle` 和 `codexDescription` 负责这个选择和回复的包装。Responses API 和 Codex 后端这两个入口都用它。用量和 Routing 保留原来的用途；用不了的描述回答被记成描述失败。这些辅助函数不解密外部的密封历史，也不修复 ChatGPT 的回复保护。

Codex 的输入框预测（#1970），即它对用户下一条消息的猜测，是这个线程的一个分叉上的另一个隐藏轮，只通过 ChatGPT 登录态发送，`thread_source` 是 `composer_predictions`。每一次都把整份对话再读一遍。`CodexPredictions` 挑它们去哪里：空的按 Codex 要求发出去，`off` 让崇云科技回答 `{"suggestion":null}` 并且什么都不发（`sentNowhere`，和标题 Off 模式一样），而一个模型 id 把它们发给那个模型。`codexPredictionsTo` 和 `codexPrediction` 负责这件事，在同样那两个入口上。一个模型的回答只有以它要求的那个 `{"suggestion": string|null}` 对象才能到达 Codex（`predictionJSON`）：纯文本从不被当作建议，因为 Codex 会把它放进用户的输入框当作他们的下一条消息，所以它不给预测，这次调用被记成预测失败（`noPrediction`）。

## 运行时路径

<a id="runtime-path"></a>

1. `handle(proto)` 读 body 和模型（`requestBody`，`requestModel`），然后调用 `serveAgent`。每条读 agent body 的路由（每个 API、count_tokens、Gemini 的、embeddings、图像、视频、System One、Codex 后端路径）都通过 [`request_bounds.go`](../../internal/gateway/request_bounds.go) 里的 `readBoundedRequestBody` 读它。它解码 `gzip` 或 `zstd` 的 `Content-Encoding`（`decodedBody`；Codex 也会给自定义 provider 的 `/v1/responses` 发 zstd，#1223）并丢掉那个头，于是发给 provider 的是普通 JSON，只有一个例外：一个 ChatGPT 账户的轮（POST `CodexBase`/responses，来自 `forwardOnce` 里的账户循环，或由 `codexUpstreamOn` 中继）会再次用 zstd 压缩，窗口最多 2 MiB，就像 Codex 自己的客户端那样发（`provider.CodexCompressed`；openai/codex 的 `responses_request_compression` 和 `http-client/src/request.rs`）。它在 body 定稿后压缩一次，每次尝试时再压缩一次。`/responses/compact`、一个 API key 的请求和所有其它 provider 都保持普通。普通发送时，一个 1.1 MB 的纯文本轮被答 503（ylorn 报告）。普通 body 是崇云科技保留并显示的那个，而 `codexDropped` 按上了线的字节判断一次重置。`codexDropped` 也把 Envoy 的 507「exceeded request buffer limit while retrying upstream」（后端失败而前端没法重试这么大的 body）读成那种重置，不论多大，被告知为 503，于是崇云科技、Codex 和 pi 会再问一次，谁也不休息（#2034）。大小限制（`defaultBodyLimit`，512 MB）按解码后的字节算（413），而任何其它编码被拒 415。它曾经是 128 MB，直到一个读了很多图像的长时间 Codex session 在解码后超过它，它内嵌的截图每轮重发，于是拿到 413，而 Codex 的五次重试全都失败（#1422，`TestImageHeavyCodexTurnIsRead`）。崇云科技自己的 413 说是它的网关限制，带上大小，并说 provider 没被问过（`overLimit`）；`writeError` 会给它不是自己拦下的任何 413 补上这是字节限制而不是模型的上下文，并提示 `/compact` 或开始一个新对话（`TestOverLimitSaysWhoseAndWhatToDo`）。除 Gemini 外的每种形态都把 413 说成 `request_too_large`，Anthropic 自己的类型，pi 的溢出表知道：pi 会压缩并再试一次，而不是停在 OpenAI 形态的 `api_error` 上（@wilsonxuuuu 报告，`TestPayloadTooLargeSaysRequestTooLargeToPi`）。`keyLimited` 同样方式读一个受限 key 的压缩 body，所以它的预留是解码后的大小。`serveAgent` 跑 [middleware](gateway-middleware.md) 链，然后 `serve`。
2. `serve` 把请求里的秘密打码（`redacted`；`redact.MaskJSON` 不动 id，也不动一个工具的名字和它那个 MCP server 的（`namespace`、`server_label`、`server_name`，#3143）；请求里的工具定义和输出 schema，按它们在各自协议里的位置找到（顶层 `tools`、`tool_choice`、`response_format`、`text`、`generationConfig`、`stream_options`、`client_metadata` 里的客户端 id 等等，以及一个 Responses `additional_tools` 或 `tool_search_output` 项的工具），除了它们的描述之外原样发出，所以用户打码的一个词不会破坏一个语法或一个枚举（#1911）；而厂商用签名封住的东西、一个思考块、Gemini 的思绪或 Responses 的加密 reasoning，按厂商写的样子回去：只有别处在请求里被打码的值，和事先打码的秘密，会以它们的占位符放回去；一个被打码过一次、至少 8 个字符长的值，会在请求里有它的任何地方再次被打码，作为精确匹配，不管周围是什么词，所以厂商关于一个占位符写的东西不会带着那个值一起回去，`redact/known.go`），把模型解析到一个 provider 或一个组，并拒绝没法提供的模型。回复在去 agent 的路上把那些值放回去（`redact.Writer`，流式的一个事件一个事件地放，整份 body 在末尾一次放）：一个模型照着给它的样子写下的占位符，或模型改写过的（花括号里的空格、丢掉一个或两个花括号、换一种大小写），只要剩下的部分点着某个崇云科技做的占位符，它就又是那个值，而一个跨事件被拆开的占位符会被留住直到完整（`redact.Restore`，`partialTail`，[`internal/redact/redact.go`](../../internal/redact/redact.go)）。一个它的 provider 和 fallback、或它那个组的模型全都跳过打码的请求（`unredactedRoute`，`provider.SkipsRedaction`：设了 *Send requests unmasked*、`Unredacted`，且每一个地址都在这台机器或本地网络上）会照 agent 写的样子发给它们；日志和最近的调用保留打码后的 body。count_tokens 和 embeddings 遵循同样的规则。一个路由组的 Jev 被告知的那一轮（那条消息、它之前用户的消息和对它的回复）同样被打码，除非 Jev 自己的 provider 也跳过打码（`askJev` 里的 `maskedState`，[`decide.go`](../../internal/gateway/decide.go)）：一个远端的 Jev 不是这个组的成员。打码是内置 plugin `redact` 做的（`gwmw.Masker`，[plugin 运行时](plugin-runtime.md)）；当设置要求打码却没有 masker 提供服务，或者它失败时，这个请求是 503，什么也不发（`redacted`，`gwmw.Masking`）。
   - 开着 *Mask personal data* 时，`redact.Categories` 里的每一种（[`internal/redact/more.go`](../../internal/redact/more.go)）都被打码，除非用户把它关掉（设置里的 `redactKinds`，`Options.Kinds`）。默认开着：美国 SSN、护照号、通过 mod 97 校验的 IBAN、紧挨着一个明说生日这个词的生日、MAC 地址，以及紧挨着 S/N 之类词的序列号。默认关着：home 目录里的用户名、提示词或 ssh 命令里的 user@host、公网 IPv4 和 IPv6 地址（私网、回环、链路本地、CGNAT 和文档保留段从来不打码）以及云存储桶名，因为 agent 几乎每个请求都发它们，而模型必须在路径或 URL 里一字不差地抄下占位符。上下文规则只在它们那些词附近跑（`rule.matches`）。读起来像地址但结尾是一个没有域名的文件扩展名（`…@2x.jpg`，`strings@base.json`；`realEmail` 里的 `fileExt`），或者扩展名前有一个倍数而那个倍数也是域名（`icon@2x.zip`，`intro@1.5x.mov`；`scaleExt`），那是一个文件名，对规则和本地模型都一样（#3029）。`ops@files.zip` 仍然是一个地址。设置的这些行来自 app.js 里的 `REDACT_KINDS`，`TestRedactKindsAreRedacts` 把它约束到同样的 id 和默认值。
   - 开着 *Find with a local model* 时（`settings.RedactModel`，这台机器自己的，由 `KeepOwn` 保留），一个本地模型找出规则找不到的东西，自由文本里的一个名字或一个地址，用同样的开关：一个名字、地址、电话、邮箱或账号号码是个人数据，一个秘密是秘密（[`internal/redact/model.go`](../../internal/redact/model.go) 里的 `modelKinds`、`modelSpans`）。`MaskJSON` 每个请求问它一次，对每段它本会打码的文本，每段一次（`withModel`）；它找到的区间和规则找到的合起来，两边都找到同一个值时保留规则那一种，而厂商或工具做的 id（`req_…`，`toolu_…`）从不被算作名字（Codex 的 `sequential_cutoff`，#3144），也不被算作秘密的那些点着一个东西的东西：一个 UUID、一个带算法名的摘要、一个文件路径（`namesThing`；模型把这三者都算作秘密）。这个模型漏掉很多中文名字（给后面的张伟，客户后面的陈建国，无论它的阈值多低），并把它找到的一个名字延伸到后面的词（「王芳，她下周一」），所以开着它时一个中文名字也会由它的姓和一个说明这里指人的词（客户、我叫、给…发、…先生、…说，用和连到另一个名字）一起被找到，而模型找到的那些在标点和称谓处被切开（[`zhname.go`](../../internal/redact/zhname.go)）；一个周围什么都没有的姓（王国的，张开的）被留下。这个模型是 OpenAI 的 Privacy Filter 的一个 q8 GGUF（1.6 GB），由 `pf-serve` 运行（[`native/privacy-filter`](../../native/privacy-filter)，从 ggml 上的 privacy-filter.cpp 构建，以 `pf-v*` 标签发布）：设置 → 隐私的 On 会下载两者（`pii.Download`，各自对着它钉住的 sha256 校验，在中国先从 hf-mirror 取，`source.chinaFirst`），并只在它们落到磁盘上之后保存设置（`/api/privacy-model`，[`privacymodel.go`](../../internal/gui/privacymodel.go)）。`pii.Find` 在第一个请求上启动 `pf-serve`（Metal、Vulkan，否则用 CPU；一个在 GPU 上死掉的会在这次运行的余下时间里用 CPU 启动），把短文本拼成 12 KB 的块并把区间映射回去，按哈希留最近 20000 个答案，10 分钟没有请求就结束它（[`internal/pii`](../../internal/pii)）。一个开着却答不了的模型（不在磁盘上、没启动、挂住）会 panic，所以这个请求被上面那个 503 挡回，而不是只带着规则的打码就发出去（`masking.model`）。

5. 最后一个候选的错误到达 agent，一个组除外（#1418，`patience.go`）。当每个成员都以一种算通过的方式失败（`busy`：一个不是代理的 408、500、502、503、504 或 529、一次配额、一次回复保护，或一个上游用一个整份回复回答了一个流式请求，无论问多少次都以同样方式失败（`didNotStream`；`passing` 的同一次重试也不动它，`TestStreamlessMemberIsAskedOnce`），或一个 429 那是短的限速而不是套餐或额度），而回复的任何部分都没有发出时，这样失败的成员会在一次暂停之后依次被再问（`replan`）。暂停是 `retryPause` 每一轮加倍，最多到 `replanLongest()`（30 倍 `retryPause`，30s），而且从不少于最近的 Retry-After；一个 Retry-After 结束在暂停之后的成员在其它成员之后被问。这在组的 `Patience` 持续期间继续。组里的一个成员用设了 `Patience` 的最内层那个（`innerPatience`，#2410），像 FirstToken（#2246）和 Sink（#2255）那样；没设就退回被问的那个组，而一个内层的 `PatienceOff` 跳过那个成员的 replan（`TestNestedGroupPatienceThroughOuter`、`TestNestedGroupPatienceInnerOff`、`TestNestedGroupPatienceFallsBackToOuter`）。`replanRounds`（12）只是一个从不先到的兜底：光暂停就加到 11 轮里的 `PatienceLongest`（用 6 时，一个设成 240s 的组在 90s 的暂停后就放弃了，real-jacket on #1418；`TestPatienceIsUsedUp`）。预算是这个组的 `Patience`，从每个成员都失败过的第一次算起，也就是 agent 本来会拿到那个错误的时候（`waitFrom`；`Group.Waits`：0 是 `PatienceDefault`，60s；-1，`PatienceOff`，把它关掉；最多 `PatienceLongest`，240s）。一个会结束在预算之后的暂停不被采用，而 agent 得到那个错误。当另一个成员也忙时，最后一个不会单独先被再试一次（`passing`）：这些成员轮流来，而一旦预算开始，同一次重试也不被采用。在预算持续期间，最后一个候选的失败被扣住（`newHoldWriter`），而一个流式的 agent 通过 SSE 注释在暂停期间被保持活着（`pauseAlive`）。这次尝试的 trace 带着 `Again`（暂停）、`Replan`（有多少个被再问）和 `Patience`（以秒计的预算）。组编辑器的「Every member busy」那一行设它。一个普通的 provider 只保留 `passing` 给最后剩下的那个的同一次重试。一个在任一次暂停里离开的 agent（那次同一次重试的或一个组的 replan）以 499 结束这个请求：不再问任何人，而它所在的那次暂停的尝试被标成 `Gone`（#1894，heng91：一个中继在它的代理关着时掉了，agent 的窗口关上了）。Routing 页面说 agent 在重试之前取消了请求并把它列为已取消，而不是让它的故事停在「2s 后再试一次」上，一个从未到来的重试（`TestAgentGoneInTheRetryPause`、`routing-agent-gone.test.cjs`）。一个回答了的尝试被记下（`served`，`answered`），供路由、affinity 和用量使用。一次尝试只在被问的时候才加到路由的 `Tries` 里，所以后面那次尝试就是网关从这个走了下去的记录，而 Routing 页面从那里说一次尝试的下场，绝不从它在顺序里的位置说（#2281，xishuchkui-code：一个 Antigravity 502 的空回复换到了下一个账户，却被说成「另一个账户修不好的错误，所以 Claude Code 收下它」）。这个记录唯一没法显示的情形是最后一次尝试在前面一次不是那种失败的失败之后被排除在它的额度之外，这时 agent 被告知前面那个错误：那次尝试被标成 `Earlier`（`routing-went-on.test.cjs`）。

## 约束与失败行为

<a id="constraints-and-failure-behavior"></a>

- 只在回复的任何部分都还没发出时才会故障转移。一个 agent 绝不会从一个上游拿到半份回复、再从另一个拿到剩下的半份。
- 一个以错误形式来的拒绝（#2400，Jichao）。一个它自己的 `message` 整个就是 `The request was rejected because it was considered high risk` 的错误，是一个旁边没有 code 的拒绝（`policyRefusal` 里的 `highRiskRefusal`）：在一个 HTTP 错误 body 里或一个流的 error 事件里，绝不在一个回答的文本里，因为那可能引用它。发它的厂商不知道是谁；它说的是这个请求被推开了，所以它像任何拒绝一样在 `RefusalRetries` 下走到下一个候选，且不让任何人休息。任何一个内容之前的拒绝 error 事件会立刻结束这次尝试（`eventRefusalError`，`stop` 和任何错误一样），所以一个把流一直开着的上游不会拖住下一个候选；一个拒绝的 stop 或 finish 标记仍然会读到结尾，用量用它，它之后的终止符也用它。内容之后，每一次写都被读一遍以发现迟到的拒绝（`refusalAfter`），所以一个 `event: error` 的名字和数据分两次写来的拒绝仍然被记下，而且什么也不重放。`TestHighRisk*`、`TestRefusalErrorDoesNotWaitForEOF` 在 [`refusal_error_test.go`](../../internal/gateway/refusal_error_test.go) 里。
- 一个请求就是一条用量记录，按它结束的方式只数一次（小一 报告：Codex 用额度时显示「5,482 · 1,094 failed」，而那些行写着「2 tries/3 tries」并且已经回答过）。当路由花了不止一次时，最终记录带着 `tries`（`rec.Tries`，来自 trace 的 `Tries`）。一次被厂商拒绝或推开的尝试（`hw.refused`，`hw.turnedAway`）仍然写它自己的记录，为了它被计费的部分和它失败的原因，标为 `handed_on`；`usage.Totals.count` 在调用数和失败数上跳过这样的记录。一个请求只有在 agent 收到一个错误时才算失败（`LostRequest`）；一次在失败尝试之后得到的回答和它并排算作重试后的回答（`Totals.Retried`，`RetriedRequest`，`retried` 过滤器）。在 `handed_on` 之前写的日志按同样方式读：日志索引把一个失败的、未被拒绝的、后面跟着同一个 route id 的另一条的记录标为 handed on（[`log_index.go`](../../internal/usage/log_index.go) 里的 `routeRows`）。按账户或路由的计数（`vias`，窗口占用）仍然数每一次尝试。一个在 Codex 自己的 ChatGPT 登录态上中继的轮，被记作那个 codex 账户（[`codex_backend.go`](../../internal/gateway/codex_backend.go) 里的 `codexServed`），所以账户卡片的窗口会计它；Routing 视图仍然点名 OpenAI 这个席位，一个 API key 的调用保持 `openai` 且没有账户，一个它的 `chatgpt-account-id` 不是这里 Codex 的 auth.json 所登录的那个账户的调用也一样（WSL 里的或另一个 `CODEX_HOME` 下的 Codex），而一行已经写成没有账户的就原样留着。那些中继的行仍然不是 lead 的回答者（`loggedAnswers`，#1367）；一个由账户回答的行、它那个作为邮箱的 `host`，仍然是。
- 每条记录以三种方式保留服务 tier（#1784）：`tier_asked` 是客户端的 body 要求的（`bodyTier`；Claude 的 speed fast 读作 `fast`），`tier_sent` 是那次尝试的最后一次请求实际带出去的，在每一次重写之后于 `forwardOnce` 记下（快速挑选、无该套餐时 Ultrafast 转成 priority）记到每次尝试的 `wireAt` 上，而 `tier_served` 只是回复说它跑在什么上面（`upstreamTier`，由嗅探器和翻译后的读取器读出），它什么都不说时是空的。路由的各次尝试同样带着 `tier` 和 `tier_served`。一个不走 `forwardOnce` 的桥（Claude 订阅、Cursor 的内置）让 `tier_sent` 保持空。代码：[`tier_record.go`](../../internal/gateway/tier_record.go)。
- 一个 agent 的快速挑选（`settings.FastPicks`，它选择器里的那个闪电，#954）也可能在 `settings.UltraPicks` 里（#1954），只有当 Codex 的某个账户在那个模型上列着 Ultrafast 时 GUI 才提供它（`provider.CanUltra`，`UltraModels`）。`fastPick` 把它的候选标为 `ultra`；对其中一次尝试，Chat 和 Responses 上带 `service_tier: "ultrafast"`，而一个在 Messages 上的 agent 把它带在 context 里（`withUltra`）交给 `forwardTranslated`，后者为 ChatGPT 后端设置 `Request.Ultrafast`。不管哪条路，都适用和客户端自己要求 Ultrafast 相同的检查，现在 Chat 上也适用：一个列表不提供它的账户被排在一个提供的同伴之后（`tierMate`），或者在没有同伴剩下时，发成 `priority`。一个 Chat body 自己的 `service_tier: "ultrafast"` 也被解析成 Ultrafast（`chat.go`）。`TestUltraPickSentUltrafast`。
- 一条用量记录在 `in` 和 `out` 旁边带着它提示的缓存（#1839）：`cache_read`（从厂商缓存里读到的 token）和 `cache_write`（缓存创建，Anthropic 的 `cache_creation_input_tokens`；`cache_write_1h` 是为一个小时而写的那部分）。`in` 两者都不含。两者写在每条记录上，0 也写，所以一个没命中缓存的提示读起来就是这样。此前的一条记录两者都没有，读作 0。每条路由都填它们：Anthropic 的 messages、Chat（OpenAI 的 `prompt_tokens_details.cached_tokens`、DeepSeek 的 `prompt_cache_hit_tokens`）、Responses（`input_tokens_details.cached_tokens`）和 Gemini（`cachedContentTokenCount`），无论是中继还是翻译、整份还是流式、一个 plugin 的 fetch，还是 Claude 订阅桥。System One 的决策调用不报缓存。`TestUsageRecordsCacheTokensOnEveryRoute`、`TestPluginUsageRecordsCacheTokens`、`TestClaudeSubscriptionUsageKeepsCacheTokens`、`TestRecordAlwaysCarriesCacheTokens`。
- 一个 key 是 Claude 登录态的请求（`claudeSignIn`：`Authorization: Bearer sk-ant-oat…`，Claude Code 以崇云科技为它的 base URL 登录了 claude.ai）从不被告知 401，也从不被告知一个说「OAuth token has been revoked」的 403。崇云科技从不转发那个登录态，所以这样的回答是 provider 在拒绝崇云科技的凭证，或是崇云科技自己的某个 Claude 账户失效了；被告知后，Claude Code 会在它每一次重试之前（一个请求十次）自己续期登录态，然后去 `/login`。任何提到 x-api-key 的错误，无论什么状态，Claude Code 也说成「Not logged in · Please run /login」。它被告知为 502，用崇云科技的话，一个 `api_error` 说着「<provider> refused magpie's credential (HTTP 401): …」，而 x-api-key 写成「API key」；而这样一个请求的其它任何错误保持它的状态，x-api-key 写成「API key」，一个流在它的 200 之后的错误也一样（`keepsSignIn`，`claude_signin.go`）。最近的调用和用量日志保留 provider 的状态和消息。任何其它 403，以及一个带崇云科技 key 或 API key 的请求，照旧被回答。这个登录态的 beta（`anthropic-beta` 里的 `oauth-…`）同样不被转发（`askedBetas`），所以一个 provider 收到的是 Claude Code 带崇云科技的 key 发出的样子；而 provider 自己的 `header.anthropic-beta` 仍然发出去。
- 一个不可能是某个 API 的回答的 2xx，就是它所代表的那个 502（`notAnAPIReply`，#1012）：一个网页（`text/html`，或一个以那样开头的 body：一个登录页、Cloudflare 的挑战）、一个里面什么都没有的 body，或一个作为 JSON 发送却不是以 JSON 开头的。每个上游请求都经过它（`forwardOnce`，以及内置客户端自己的：ChatGPT 后端的 `/responses`），所以它像 502 那样故障转移、休息并被记下，它的理由点名那个页面的标题。只窥看最前面的几个字节，而流本来也要等它们，一个压缩过的 body 原样留着。
- 来自 Zhipu 或 Z.ai 的一个带着平台拒绝封套的 2xx（`{"code":1000,"msg":…,"success":false}`，它们 `/api/v1` 的 Responses API 用它回答一个被拒的 key）就是它所代表的那个拒绝（`forwardOnce` 里的 `provider.ZhipuEnveloped`）：一个被拒的 key 是 401，一个限额或没有余额是 429，按 Zhipu 的错误码给，所以它像那些一样故障转移和休息，而 agent 被告知原因。`TestZhipuResponsesRefusalIsRefusal`。
- 一个流式请求在它的厂商什么都不说时绝不被留在沉默里。`holdWriter.watch` 在每次尝试旁边跑：超过 `keepHeldAfter`（15s）后它给一个被扣住的尝试的 agent 发这个流的 200 和 SSE 注释（`keepAlive`），不含这次尝试的任何内容，所以同一条流里另一个候选仍可能回答；一旦回复通过，它在 `keepaliveEvery` agent（`failTo`），不是一个状态（coeo91 报告）。一个短于 `keepHeldAfter` 的等待什么也不发，所以它的 429 保留自己的 `Retry-After`。否则像 Cloudflare 这样的一个前置代理（125s）会结束这个请求（#947）。Gemini 的流得不到注释（#934）。一个随后忽略 `stream:true` 而用整份回复回答 200 - 一个在休息的候选最后才被试（`restLast`）。在休息的候选之中，一个请求只问那个休息最早结束的，平手时按顺序第一个（`probeOne`，#1799）。其它不被那个请求问，所以一个挂了的成员不会被它那段休息本该为它省下的每个请求都问一遍，而一个整体挂了的组每个请求只花一个上游请求，而不是每个成员一个。每个就绪的候选仍按它的顺序被问。一个孤零零的候选在它休息时仍被试，因为没有别的了。trace 仍列出每个成员，休息的那些带着它们的休息。只读休息，而一个关于请求内容或它的模型的失败不让任何成员休息（一个模型拒绝只让 `restID` 休息），所以两者都不会让一个成员被排除。`count_tokens`、embeddings 和 rerank、图像账户和一个组的 System One 决策模型也一样适用。一个 Codex 重置（`autoReset`）仍会看遍每个候选。这就像 AxonHub 的错误感知负载均衡：休息和它的退避是那个会衰减的惩罚，而最早回来的成员就是被问去证明它回来了的那个。超出自己配额的 key 连这样也不被问，连最早回来的那个或孤零零的那个也不问（#1772：四个 Ollama Cloud 的 key 那一周出局，每个请求都被再问一次并被拒）。再次给出的拒绝会在崇云科技带着它自己偏移的时钟上说明它们何时再被问（`heldClock`：「20:12 UTC+8」、「Oct 16 09:00 UTC+8」），网关的其它被扣住的错误也一样（一个封顶的窗口、一个用完了的搜索者或描述者）：读它的可能是另一台时钟上的一个 Remote chongyun 用户。当剩下的每个候选都是 key（不是订阅账户，它的重置 `autoReset` 可以花掉）在一次 429 或 402 之后因配额或额度而休息时，一个都不被问。第一个的拒绝再次给出（`quotaHeld`，它的话留在休息的 `said` 里），说明它何时再被问。当最后剩下的那个 key 也这样被拒时，它也休息，和它前面的那些 key 一样。任何在没有厂商 `Retry-After` 的情况下到达 agent 的 429，而每个试过的候选都在休息，都带一个：到它们之中第一个回来还有多少秒（`soonestBack`）。一个没有说它何时回来的配额拒绝休息 `quotaRest`（15 分钟），或 provider 自己的以分钟计的 `quotaRest`（`Provider.QuotaRestFor`，最多 `MaxQuotaRest`，8 天；`chongyun provider quota-rest <id> 7d`），或直到用户说它的配额回来的那个时刻（`QuotaResetAt`，`Provider.OwnQuotaRest`；`chongyun provider quota-rest <id> until 08:00`，或按厂商时钟的 `until 00:00+08:00`；#2008，一个免费档的「today's free-model token quota」）。两者之中最后被设的那个算数。厂商点名的时间压过它，它的 `Retry-After` 也是，除非那个超过 `longestWait`（一小时）而被截到它，而用户自己的休息更长：那时用户的算数（`TestQuotaRestsUntilTheTimeOfDaySet`）。一个既列在 `keys` 里又列在 `key` 里的 key 是一个候选（`KeysOn`），不被问两次。`TestAllRestingAnswersFromRest`、`TestOwnQuotaRest`、`TestQuotaHeldOnlyForKeysOutOfAllowance`、`TestFirstKeyListedTwiceAskedOnce`。
- 一个已知要花得比这个请求少的模型的成员不会被问这个请求（[`fallback.go`](../../internal/gateway/fallback.go) 里的 `roomy`，在 `serve` 里规则、affinity、图像过滤器和 `pinTo` 之后，在 `probeOne` 之前；dgqyushen 报告：OpenCode Zen 的免费 DeepSeek V4.1 Flash，200K，在一个组里排第一，而它的一个 1M 订阅排第二）。这是发送前的一次检查，不是一次重试：这个请求的 token 按溢出降级那样估算（`estimate`，文本、工具参数和 schema 上的字节数除以 4），而一个窗口已知（`windowOf`：provider 的 `Contexts`、目录、`ContextOf`）且不大于它的候选被从候选里和 trace 的顺序里去掉。被问了这样一个成员只会拒绝，而一个不为一个短于 `tooLongUnsaid` 的 1.2 余量的请求说原因的拒绝，会在下一个成员还有空间时作为厂商的错误到达 agent；它还花掉了那个成员额度上的一个请求。一个被 affinity 留在某个成员上的对话在长大超过它时会移动。窗口未知、body 解析不了、候选中只有一个模型、或没有候选装得下这个请求时，什么都不排除：那时第一个被问，而它的溢出作为一次溢出来到 agent，好去压缩（`withRoom`、`failOverflow` 和 `tooLongUnsaid` 留给估算漏掉的那个窗口，它在代码上算低、在 CJK 文本上算高）。一个比最小窗口每 token 四个字节还短的 body 不被解析。`count_tokens`（对组里第一个成员的计数，不是发送）和 System One 的决策模型（短的决策文本）不走这一步。被排除的那些是最后手段：当最后一个还有空间的候选因它的配额或额度失败（`failQuota`/`failCredit`），而它之前没有以别的方式失败（`other`），并且没有账户被钉住时，那些没在休息的被排除者最后还是被问，它们的行被加到 trace 的顺序里，而失败的那个像其它一样在最后一个之前休息。它的溢出让 agent 去压缩，而 429 只让它等一个几小时之外的配额（Kai 报告：两个 Claude 账户都花到了第二天，Claude provider 的 Fallback 是一个 272K 的 Codex 模型，在一个更长的对话下，从未被问）。另一种失败（一个忙的厂商、一个坏 key）仍然照原样到达 agent，那个小的没被问。Routing 页面只通过一个成员从路由顺序里消失来表示它被排除且没被问。`TestMemberTooSmallIsNotAsked`、`TestMemberTooSmallIsTheLastResort`、`TestClaudeAccountsSpentFallBackToCodex`、`TestConversationOutgrowingItsMemberMoves`、`TestRoomyLeavesWhatItCantJudge`。
- 路由只在没人回答过这个对话时才决定谁先走。Affinity 在它的缓存还值得时留住那个回答者。Auto mode 在最后一次回复从缓存读出并写入缓存的 token 两者之间至少 `cacheWorth`（1024）时（用量的 `CacheRead` 加 `CacheWrite`，传给 `answered`）并且缓存不是冷的（`cacheCold`，5 分钟）时，跨轮留着它。超过 5 分钟后它留着，只要厂商说它为这个对话保留至少 `cacheWorth` 个 token 一小时（`hourCache`，#2302）：一个带 Anthropic 的 1 小时写入的回复（`cache_creation.ephemeral_1h_input_tokens`，用量的 `CacheWrite1h`，就像 Claude Code 向一个订阅要的那样）保留它读到的加上那些 `cacheHour` 的，后来在同一个账户和模型上把它整个读到的回复重新开始那一小时，而读得少的（被移动、被压缩）就丢掉它。这个黏性也把它留在磁盘上（`cacheHour`，`cacheHourAt`），而一个组的规则在那同一小时里保持这一轮的 effort（`keepsEffort`）。不报 1 小时写入的厂商不变。`TestAffinityKeepsAnHourCachePastFiveMinutes`、`TestHourCacheAfter`。写了什么是要算的：第一轮什么都不读而写下整个提示（Anthropic 的 `cache_creation_input_tokens`），而第二轮留下来读它，而不是作为 `no-cache` 移走并在别处重建它（vilicvane 报告）。这个黏性把两者都留住，在磁盘上也留（`affinity.json` 的 `cacheWrite`，在旧文件里没有而读作 0，所以这样一个黏性只按它的读来判断），而 trace 的 `Affinity.CacheWrite` 让 Routing 页面说出读了什么和写了什么。一个不报就把提示缓存着的厂商（OpenAI 的自动前缀缓存、Gemini）对一个没读过的轮两者都不说，所以那一轮被发出的提示（用量的 `Input`）就当作那次的写入，而它的第二轮也留着；一个完全没报用量的回复照旧算作没有缓存。`TestAffinityKeepsACacheJustWritten`、`TestAffinityKeepsACacheTheVendorKeptSilently`、`routing-affinity-cache-write.test.cjs`。
- Strict（`strict`，#1797，miniers）绝不把一个对话移到另一个 key 或账户（`who`）。它的黏性像 session 的一样被留着，而在它新鲜的时候 `affine` 只留住那个 `who` 的候选（`strictOnly`）：它的其它模型留着，所以一个组的规则仍能在它们之中挑选，但不问别的账户、key 或 provider，而一个在休息或用完的还是被问。在那里的一次失败到达 agent，并像非孤独候选的那样让账户休息（`strictAlone`），所以新对话去别处。规划之前，`strictKeep` 把那个被卡住的账户从挡着新对话的地方拿回来：一个用量上限（`pl.capped`，`capHeldOnly`），于是这个对话越过它继续。一个因它可能不能花的额度而被挡住的账户被答 429，点名那个账户和 Strict，而且什么也不到厂商，而不是被移动。一个被移除、被关掉、被挡或对调用 key 不允许的账户就没了，而对话像在 session 下那样移动。trace 即使只有一个候选也说 `strict`。`strict_affinity_test.go`、`stays-strict.test.cjs`。
- 轮换中（`rotate`），一个没人回答过的对话去那个 key、账户或模型——在 provider 的模型或组最近 `heldFor`（30 分钟）里回答过的其它对话最少的就是它（`leastHeld`，#946）。平手、在休息的那些和一个组里有组的都保持路由的顺序。带上 session affinity，一个组的两个 session 仍留在不同的模型上。
- 一个握着额度的 ChatGPT 账户在它的窗口之外仍然回答，厂商花掉那些额度。这是默认。设成不花它们（Usage 卡片的 *Use credits*，`chongyun quota credits <account> off`），这个账户按崇云科技最近一次对它的窗口的读数（`provider.Allowances`，大约每分钟刷新一次）在某个窗口的 100% 上被挡住直到它续期，于是别的账户、组和 fallback 来接这个请求。设在那个账户上的上限（1–99%）优先。和上限不同，这个挡住是在厂商自己的 100% 上，所以一个被允许花掉它重置的账户在那里花掉一个，既在每个候选都被挡住时，也在最后一个被拒之后。一个被做出的重置忘掉这个账户缓存的配额（`renewedNow`），所以两种挡住都不会比它们重新开始的那些窗口活得更久。

- Codex 自己的某个模型在后端路径上没有路由可做（`codexAccounts` 为 false：一个 ChatGPT 账户、没有用量上限、没有 key 限制、什么都没钉住），就照 Codex 发出的样子中继，用 Codex 自己的登录态，它的字节和头不变，它的回复照来时流式出去（`codexUpstreamOn` 没有账户）：路由是为多于一个账户建的，而那条路也把这一轮的原生压缩留给后端。在那之前，上面什么都不会被再问，所以一次过载直接落到 Codex，而 Codex 自己不重试后端的 `server_is_overloaded`（夜松云 报告）。现在一次瞬时过载（`codexBusy`：`busy` 叫作 busy 的那些、一个 529、一个说 overloaded 的 503、后端流内的 `response.failed` 带 `server_is_overloaded`（#1418）；绝不是 429、用量上限、边缘节点掉的连接（`edgeSaidDrop`）或一次重置（`codexReset`））会被向同一个账户、同一个 body 和头再问，最多 `lastRetries` 次，在 `retryPause<<n` 之后，像账户循环问它最后一个账户那样，而且只在回复的任何部分到达 Codex 之前。一个流通过一个 `holdWriter` 为它被扣住，让它的 reasoning 过去（`thinkingShown`），在多次尝试之间超过 `keepHeldAfter` 仍被保持活着（一个 `keptAlive`），所以 Codex 看到的是这个流的头和注释，绝不是一次失败尝试的帧。过载不让任何东西休息。重试用完之后，一个 codex 订阅有 fallback 的轮（`codexFallsBack`；绝不是一次压缩）就继续到那些 fallback（`codexFallBack`：这一轮作为 `codex/<model>` 被服务，账户被排除在候选之外，`fallbacksOnly`，同一个 keepalive 由 `handedOnKey` 带过去）；没有 fallback 时 Codex 得到最后一次尝试的失败，就像后端说的那样。每次尝试是一条 `HandedOn` 用量记录和 trace 里的一次尝试。一次成功照旧被中继，没有重试或 fallback 剩下时什么也不被扣住（`TestCodexOneAccountOverloadAskedAgain`、`…StreamOverloadAskedAgain`、`…OverloadBounded`、`…OverloadFallsBack`、`…OverloadKeptAlive`、`…RefusalNotAskedAgain` 在 [`codex_one_account_overload_test.go`](../../internal/gateway/codex_one_account_overload_test.go) 里）。
- 一个它的厂商撤回了登录态的订阅账户（`provider.SignInRevoked`：401 `token_revoked` 之类，#1793）以 `failAuth` 失败：下一个成员立刻被问，什么也不休息，而这个账户被标记（[`signin_revoked.go`](../../internal/gateway/signin_revoked.go) 里的 `noteSignIn`）。在它有那个凭证期间，它后来的请求不被发出：`forwardOnce` 用崇云科技自己的一个 401 回答它们（`revokedReply`），所以它们也照旧往后传。在崇云科技自己的某个账户上做压缩（`compactOn`）把被标记的那个排在最后。一个 key 的 provider 回答同样的话则照旧休息。
- 一个超出自己限制的 sub2api key 回答 429 `api key 7天限额已用完`（或 `日限额`、`5小时限额`），作为 `rate_limit_exceeded`。它是超出配额（`plannedWords`），不是被限速：它休息到它填满的那个窗口续期，按它最后读到的窗口，如果它们这么说；否则 `quotaRest`，而它的窗口被再读一次（`staleKeyAllowance`）。一次发现那个窗口不再满的读数（中继面板里提高了限制，或 key 的用量重置了）解除这次休息（`renewed`，通过 `provider.OnRenewed` 告知），就像花掉一个 Codex 重置对账户做的那样；这个 key 的其它休息留着。在它因窗口而休息期间，它们每次它被规划时都被再读一遍（`restingOf`，最多每分钟一次），所以这在没有按它们权衡它的地方也成立：一个有顺序的组。那个中继对所有人都没有账户了（503 `No available accounts`，或后来版本的 429 `All available accounts are currently rate-limited`）对这个 key 的窗口什么都不说：它像任何失败或限速那样退避，绝不退到那个窗口。一个 key 的窗口只算它自己的花费，所以别的用户把中继的账户用光表现为那些错误，而不是在窗口里。

## 远端崇云科技 API

<a id="remote-magpie-apis"></a>

`GET /v1/magpie/trace` 回答这个网关所决定的路由，给同一台电脑上不服务它的另一个崇云科技，它的控制台把它当成自己的 Routing 页播放（#2606）。一条 trace 点名账户和它们的邮箱、它们服务了什么、session id、一个文件夹的最后两段以及账户为什么休息；它不含提示文本也不含 key。所以它只回答 `local(r)`：来自另一个地址的请求被拒 403，来自回环但带着一个代理的转发头（这里的一条隧道或 Tailscale Serve）的也是，而网关被共享时的 LAN 请求也是，不管它带着什么 key。Rebinding、`Origin: null` 和 `*.localhost` 的页面在它之前就被 `lanGuard` 和 `corsGuard` 挡住，和每条路由一样。一个被限制在某个预算、模型或账户上的网关 key 被以 `KeyHeldCode` 拒绝，就像 `/v1/magpie/concurrency` 和 `/v1/magpie/quotas` 拒绝它一样。它回答 `Server.Trace` 持有的东西，加上这个进程的 `pid` 和 `serves`（启动它的那个命令，`Serves`），所以一个调用方可以像页面自己的 `/api/gateway/trace` 那样用 `after` 和 `wait` 长轮询它。`/` 也加上 `pid` 和 `serves`，但只给一个回环请求。`Server.gatewayTrace` 在 [`trace.go`](../../internal/gateway/trace.go) 里，而 `TestGatewayTraceIsLoopbackOnly` 在 [`trace_peer_test.go`](../../internal/gateway/trace_peer_test.go) 里，`TestHeldKeyToldNoAccounts` 在 [`quotas_held_key_test.go`](../../internal/gateway/quotas_held_key_test.go) 里。

一个远端 provider 服务对话、token 计数、System One、embeddings、rerank、语音转文本、图像生成/编辑和视频创建/状态/内容的 API。Gemini 客户端通过本地的 Gemini 适配器进来，并和其它对话客户端一样走同样的模型路由。Responses 用 HTTP/SSE；它的 WebSocket 路由仍然回答 426。发现和较老的对端行为在[provider 与账户](providers-accounts.md#remote-magpie)里描述。
`GET /v1/magpie/limit`（[`key_limit.go`](../../internal/gateway/key_limit.go) 里的 `keyLimit`）回答请求带着的那个网关 key 的限制（`access.Caller`），别的都不回答：除了它的 key，它不从请求里读任何东西。一个 key 可以同时握着最多五个限制，各在自己的窗口里，而一个请求需要每一个都够（#2227，`budget.Reserve`：每个窗口一次预留，而一次拒绝点名那个最晚重置的已花限制）。存下的 key 把第一个限制留在 `limit` 里，那是较老的崇云科技读的，其余留在 `moreLimits` 里。答案的 `limit` 是那个把 key 握得最紧的（`budget.Binding`），较老的客户端读它，而 `limits` 是它们每一个（`budget.All`）。把一个 key 握在它的限制上是 Key limits plugin 做的事，在网关的预算点上（[plugin 运行时](plugin-runtime.md#gateway-extension-points-p3-budget)）：它关着时，一个被限制在一个限制上的 key 得到 503，什么也不发。一个本地的崇云科技用它每一个远端 key 去问它，为那个 key 在它的 Usage 页面上的卡片（#1547），每个限制一个窗口。

System One 用 [`decide.go`](../../internal/gateway/decide.go) 里的 `RouteDecider` 和 `postDecide`，每一跳去掉一个 provider 前缀，并保留状态、问题和厂商错误。一个点名一组决策模型的模型（`provider.Group.Decides`：每个成员都是一个决策模型；[`decide_group.go`](../../internal/provider/decide_group.go) 里的 `cleanDecisionGroup` 拒绝混合的那种、在一个 chat 组里面的那种，以及它上面的模式、规则、effort 或快速模式）改为去 [`decide_group.go`](../../internal/gateway/decide_group.go) 里的 `serveDecisionGroup`（`decisionGroupOf`：`group/<id>`，或由 `GroupFor` 给出的一个组的 id 或名字）。它用 `planGroup` 规划这些成员的 key 和账户（`perKeyBarred` 保留一个只做决策的 provider 的 key：`DecidesModel`），照 chat 那样施加一个网关 key 的模型和账户限制以及暂停规则，并依次试每个候选：一次 `retryable` 的失败而它不是请求自己的错（`shapeRefused`、`promptRefused`、`protectionRefused`、`zdrRefused`）让它休息（`decideFailed` → `restAfter`）而下一个被问；最后一个的回答被传下去。每次尝试都是一条路由的一次 `Try`；为那个回答写一行用量。一个决策模型的组分类器以同样方式故障转移（`askDecisionGroup`，`decideRefused` 带着厂商的状态）。一个决策组被挡在 agent 的目录之外（`groupEntries`），而向它问的一个对话被拒 400 并指向 `/v1/systemone`。一个有若干 key 或账户的单个决策 provider（TypeSafe Jev 有一个 key 超出配额，fflake33 报告）以同样方式被问，在 `/v1/systemone`（`serveSystemOne`）和作为分类器（`askClassifier` → `askDecider`）：`decideKeys` 按它路由的顺序规划它的 key（Smart、In order），`probeOne` 只留下那个最早回来的休息中的，而 `serveDecideTries`/`askDecideTries` 照一个组那样依次问每一个，一个被拒的休息。在那之前，每一次调用都去它的第一个 key，不管其它 key 的状态。一个被限制在某些账户上的网关 key 只在那些账户上被问（`allowedCandidates`），而当它们中没有一个服务这个模型时被拒 403。`TestDecisionProviderKeysFailOver`。
[`embeddings.go`](../../internal/gateway/embeddings.go) 中继检索的 body 和选项（`serveRetrieval`），而 [`transcribe.go`](../../internal/gateway/transcribe.go) 把语音转文本的 multipart 表单照发来的样子穿过它，只重写模型和一个在该表单自己边界下的被打码的提示（#2053），[`draw.go`](../../internal/gateway/draw.go) 把图像发到远端的 images API，而 [`video.go`](../../internal/gateway/video.go) 为之后的轮询和下载包装远端的任务 id。[`remote_magpie.go`](../../internal/gateway/remote_magpie.go) 里的 `passOnCaller` 提供调用方/session 的头而不替换发出去的 User-Agent。对话转发保留 Claude Code 和 Codex 的客户端头（包括 Codex 的 `originator`），所以远端后面的中继能认出它们。决策、检索和媒体的请求在它们自己的调用点设置崇云科技的 User-Agent，所以远端接受它们的归属。厂商收不到任何调用方标记。

一个自定义 provider（没有账户，没有预置套餐的视频）以同样的 OpenAI 方式做视频（#1446，`customVideomakers`），但只用它自己取到的列表标着 `"kind": "video"` 的那些模型（`catalog.LiveVideomakers`）或者用户标为视频模型的那些（设置的 `ModelKinds`，`provider.SetModelKind`，编辑器里一个模型片的右键 *Makes…*，#1399）；光一个名字永远不会让一个模型成为视频制作者。一个被标为图像模型的模型被用来画（`Drawers`）并离开视频制作者，而一个被标为视频模型的离开那些画图者；只有配了 base URL 的 provider 能被标（`MarksKinds`）。开始、轮询和内容都去 `videoBase`（它的 Chat base，否则是它的 Responses base）`+ /videos`，带崇云科技的 User-Agent（或 agent 的，`passUserAgent`）且不带调用方的头。它的 id 以那个 key 的指纹结尾（`customVideoID`，`markedKey`），所以一次轮询和它的下载都落在启动那个视频的 key 上。一个网关 key 的账户和模型限制适用于全部三条路由（`videoAsker`，`videoModelHeld`），也适用于 Grok 和 Volcengine 的轮询和下载。

## 关掉 provider 搜索

<a id="turning-provider-search-off"></a>

[设置](../../internal/settings/settings.go) 的 `searcher: "off"` 关掉崇云科技靠 provider 的搜索，包括 Kimi Code 和 WorkBuddy 的搜索服务以及 Google 登录态单独发出的搜索请求。配置好的 Search API 仍按它们存下的顺序跑；在这个设置关着时，失败绝不退回到一个 provider。在没有就绪的 Search API 时，[`canSearchFor`](../../internal/gateway/search_kimi.go) 不会提供崇云科技那个替补搜索工具。`searchesOwn` 是「一个 provider 为它自己的模型搜索」的那一个检查（Kimi Code、WorkBuddy、一个 Google 登录态），所以 `ownSearcher` 和另一个崇云科技读的模型列表（`webSearchOf`，它接着说没有搜索）也跟着它走。一个 provider 在客户端协议上的原生搜索不变。一个空的 `searcher` 仍然自动挑一个 provider；一个不可用的、被点名的 provider（没了、关了、不能搜）仍然退回那个挑选。一个可用但搜索失败的 provider 不会被另一个 provider 替换（见下文）。

[`webSearch`](../../internal/gateway/search.go) 强制走只用 API 的那条路。覆盖的是 `TestSearchProviderOff`、`TestSearchProviderOffForwarding`、`TestSearchProviderOffTellsRemoteMagpie`、`TestSearcherChosen`、`TestSettingsSearchProviderOff` 和 `searcher-pick.test.cjs`。

## WorkBuddy 的搜索服务

<a id="workbuddys-search-service"></a>

一个 WorkBuddy 套餐的模型（中国版和 WorkBuddy AI 的，自内置的那个退役后由 plugin 服务）自己没有搜索工具。在崇云科技里没有别的会搜索时，`canSearchFor` 是假的，而 Claude Code 的 WebSearch 回来是空的（#1798）。`wbSearch`（[`search_workbuddy.go`](../../internal/gateway/search_workbuddy.go)）照 WorkBuddy 的 CLI 那样问这个套餐自己的服务：POST `<site>/agenttool/v1/search` 带 `{"query","type":"text2text","max_results":5}`，由 `Provider.Sign` 签名并由 `Provider.Do` 发出，所以一个已迁移的账户走的是 plugin 的 fetch。`searchesOwn` 只为这个套餐自己的模型点名它，在崇云科技挑的搜索者之前，和 Kimi Code 一样。一个 `{code, msg}` 的拒绝（15001 是它的搜索配额）被报成一个错误，绝不报成没有结果。覆盖的是 `TestWorkBuddyPluginSearches`（Claude Code 那个字面的 WebSearch 请求、真实服务的回复字节、那个配额拒绝和搜索被关掉）。

## 翻译过的 Responses 回复里的搜索结果

<a id="search-results-in-translated-responses-replies"></a>

当为一个模型做了搜索（`searchReply`），或一个 Responses provider 的搜索被解码来翻译时，它的 `KSearch` 事件和被收集的 `Search` 部分带着那个查询和找到的页面。[`responses.go`](../../internal/gateway/responses.go) 的 `responsesEncoder.event` 和 `renderResponses` 通过共享的 `responsesSearchItem` 把这些作为完成的 `web_search_call` 输出项返回。那个 action 说是 `search`，同时带 `query`（较老的客户端）和 `queries`，并把非空的来源 URL 列在 `action.sources` 里。一次没有来源的实际搜索有一个空列表；光一个文本回答不产生任何搜索。

这个流添加并完成每个搜索项，发出 `response.web_search_call.completed`，并在最终响应的 `output` 里保留同一个项。搜索事件在搜索跑完之后才到，所以不编造更早的进展。搜索项在文本、reasoning 和客户端工具调用之间保持它们的顺序。它们带来源，而不是编造的 `url_citation` 标注：共享的搜索结果在模型的回答里没有引用偏移。原生 Responses 的中继不变。一个在下一个输入里把那个项带回来的客户端（Codex 重放它的输出）什么也不失去：`parseResponses` 没有 `web_search_call` 的分支，照旧把它留下。

这让一个 Responses 客户端能验证搜索被执行并显示来源链接，而不用另发一个 Anthropic Messages 请求。覆盖的是 [`responses_search_test.go`](../../internal/gateway/responses_search_test.go) 里的 `TestResponsesSearch` 测试和 [`search_test.go`](../../internal/gateway/search_test.go) 里 `TestWebSearchForAModelThatCannot` 的 Responses 用例。

当一个被 `searchReply` 问到的 provider 正在排队或思考、只发着 keepalive 或 `response.in_progress` 时，`askTranslated` 用 `readSSEAlive` 读它，并在 `keepaliveGap` 之后传下一个 `KAlive` 事件，别的东西都没发。它不是回复的什么：`searchRounds` 不收集就把它传下去，而 `relay` 把它当作 provider 发出了声音，开始客户端的流并发出客户端自己的 keepalive（`enc.keepalive`）。在那之前，`relay` 一直等到第一段内容才做出客户端的编码器，于是 Codex 只听到被扣住那个流的注释，而它的空闲超时不算注释，于是在约 315s 后挂断（#2316）。任何 `KAlive` 之前的错误仍然是一个别的账户可以回答的状态。覆盖的是 [`search_queue_test.go`](../../internal/gateway/search_queue_test.go) 里的 `TestSearchQueueKeepsCodexAlive`。

## 哪些 provider 为另一个模型搜索

<a id="which-providers-search-for-another-model"></a>

`Searchers()`（设置 › 网页搜索的选择器）和 `autoSearcher`（崇云科技自己的挑选）按 `searchRank` 取一个 provider，按 `searchableModel` 取它的模型，用的正是那些让一个 provider 自己的搜索工具生效的规则（`searchesItself`，`modelSearches`，`remoteSearch`）。一个只为自己的某些模型搜索的 provider（`searchModels`：Command Code 的 Provider API，`partSearcher`）只带着那些模型被提供和被挑选，绝不在 `x-cmd-zdr` 之下；在那之前，它那些会搜索的模型被从两者里都排除（01huadalang 报告）。一个 plugin 的 provider，其列表标着 `searches` 的那些模型也是如此（`pluginSearches`：一个在被用普通文字要求时自己搜索网页的模型，目录里的 `WebSearch` 是 "native"）：它在不带搜索工具的情况下被问，而 `searchWith` 收一个点着一个链接的回复。在那之前，每个 plugin 的 provider 都被排除，不管它的模型做什么（01huadalang，10-20，Trae 那个搜索模型的）。一个客户端对这样一个模型自己发的 `web_search` 仍然得到崇云科技的搜索者。一个没有任何模型会自己搜索的 provider，比如一个什么都没标、其 `config` hook 也没设 `searches` 的 plugin，不是搜索者：它的模型被给上崇云科技的 `web_search`，而那一行的 `searchLeftOut` 点名它。覆盖的是 `TestCommandCodeSearchesForOtherModels`、`TestPluginSearchModelIsASearcher` 和 `TestSearcherChosen`。

## 一个失败或什么都没找到的搜索者

<a id="a-searcher-that-fails-or-finds-nothing"></a>

`modelSearch` 先问在设置里挑的搜索者（或崇云科技挑的那个）。`searchWith` 分开三种结果：一个错误、一个搜索过但没点名任何页面的回复（`errFoundNothing`），和一个根本没有搜索的回复，没有 `server_tool_use` 也没有 `web_search_tool_result`（`errNotSearched`，那也算什么都没找到）。最后一种是根本没跑搜索的厂商：工具被丢掉或没被用，而模型用它知道的东西回答。

一个崇云科技自己挑的搜索者让位给 `Searchers()` 里的下一个，总共最多三个（#669）。那个退让不是无声的：`searchingInstead` 把先被问的搜索者（`instead`）和它为什么没搜（`why`，`nothingFound` 或 `notSearched`）放到那个搜索的 `CallFor` 上。回答了的那个搜索的 Routing 行说出先被问的是哪个搜索者、为谁问的、它为什么没搜，以及哪个替它搜了（`kindWhy`）。

一个在设置里点名的搜索者不让位给任何别的 provider。它的错误回到模型，而 `webSearch` 接着去问那些搜索 API，如果有任何配好的话。`namedFailed` 留着它上一次没做的那个搜索，在它下次搜索时被清掉。设置 › 网页搜索在那一行帮助的开头显示这个（`SearcherFailed`，`searchFailed`），在它的省略号之前。Gearclickist 报告 挑了 Grok。他们的 grok-4.7 那些行大约 1.3k token，这是一个 Grok 没跑搜索的请求的大小（在我们那个账户上，一个真搜索了的要 6k-66k）。于是每一次搜索都接着去了 Codex 的 gpt-6-astra，一个他们没挑的更贵的模型。在这之前记下的、设了 `picked` 的行仍然照旧读。

覆盖的是 `TestPickedSearcherIsNotHandedOn`、`TestSearchInPlaceOfAutoSaysWhy`、`TestSearcherFindingNothingGivesWay`、`search-instead.test.cjs` 和 `searcher-pick.test.cjs`。

## 一个副模型想得多深

<a id="how-hard-a-side-model-thinks"></a>

设置 › 模型在图像识别的模型和搜索者的模型旁边各有一个小片（MOMO 报告）：[设置](../../internal/settings/settings.go) 里的 `visionEffort` 和 `searcherEffort`，是 `catalog.EffortRank` 里的一个或空。那个小片只提供模型自己的等级（`ModelEfforts`：`Efforts`，从最弱的开始；设置里读到的 `visionEfforts`，`searchEfforts`），而对一个等级未知的模型什么也不提供。一个被挑的等级在这次调用发生时配到模型的等级上（`sideEffort`，`fitEffort`），所以一个存下的等级比一次模型更换活得更久。空着就保留崇云科技自己的：图像识别用模型有的最弱那一级（`classifyEffort`），搜索者完全不用等级。只有这两个调用带着它（[`side_effort.go`](../../internal/gateway/side_effort.go)）：

- `askVisionWith` 发 Chat 的 `reasoning_effort`；那个图像缓存键（`describe`）里带着那个等级，所以一个新等级会再读一次图像。
- `searchBody` 发搜索者的 Anthropic body 的 `thinking`（`none` 时是 `disabled`，否则是 enabled 并带 `budgetOf` 的预算，`minimal` 是 1024）和 `output_config.effort`，除非那个厂商模型是比自适应思考更老的 Claude。网关的翻译接着把它配到那个厂商：对新的 Claude 是自适应思考或 `between_tools`，对 Responses 是 `reasoning.effort`，对 Code Assist 和 Antigravity 上的 Gemini 3 是 `thinkingLevel`。
- 一个被挑的等级按它的预算提高这次调用的 `max_tokens`（`replyRoom`），这样思考不花回复的额度；模型自己的上限仍然封顶。
- 一个为自己的模型搜索的 provider（`ownSearch`，Kimi Code 的搜索服务）不收到任何等级。一个退位的搜索者收到配到它自己模型上的等级。

覆盖的是 `TestVisionEffortPicked`、`TestVisionEffortOnAnthropic`、`TestSearcherEffortPicked`、`TestSearcherEffortOnGemini`、`TestSideEffortChecked` 和 `side-effort.test.cjs`。

## 一个搜索 API 的 base URL

<a id="a-search-apis-base-url"></a>

每个搜索 API（[`provider.SearchAPI`](../../internal/provider/search_api.go)）有一个可选的 `url`，它的 base URL：一个用户自己的、像那个 API 那样回答的端点（#1580）。空就是厂商自己的（`SearchVendor.Base`）；SearXNG 没有，所以它的 URL 是必需的。`check` 只接受一个带 host 而没有 `?query` 或 `#fragment` 的 `http://` 或 `https://` URL，因为 `askSearchAPI` 把厂商的路径接在它后面（`/search`、`/res/v1/web/search`、`/v2/search`、`/v1/tools/search`），而它末尾的斜杠被去掉了。这个请求走网关的客户端，所以它像厂商自己的地址那样跟随崇云科技的代理设置（`TestSearchFollowsTheSearchersProxy`）。

那个 key 只发给那个 URL。Go 在一个到另一个 host 的重定向中保留 Brave 的 `X-Subscription-Token` 和 Exa 的 `x-api-key`，所以 `askSearchAPI` 不跟随一个。那个 3xx 就是那个错误，并且它点名搜索被发到了哪里。崇云科技不附带也不列出任何第三方的搜索端点；那个 URL 永远只是用户的。

一个用户设下的值绝不被厂商的默认值替换。在设置 › 模型 › 网页搜索里，那个字段在每个 API 的 key 下面，以厂商自己的地址作为它的占位符。挑一个已经加过的 API 会填上它存下的 URL，所以只带一个新 key 的 Add 保留那个 URL，而不带 key 的 Add 只改那个 URL。在 CLI 上，`chongyun search add <api> <key>` 保留之前设的 URL，而 `url=` 后面什么都不跟就把厂商自己的放回去。备份和同步带着 `url` 和这个条目的其余部分。

覆盖的是 `TestSearchAPIAtItsOwnBaseURL`、`TestSearchKeyStaysAtItsBaseURL`、`TestSearchAPIBaseURLFromSettings`、`TestSearchCLI` 和 `search-api.test.cjs`。

## 搜索 API 的顺序，以及一个被关掉的

<a id="the-search-apis-order-and-one-switched-off"></a>

`provider.SearchAPIs` 按存下的顺序给出搜索 API，也就是 `apiSearch` 问它们的顺序，略过一个没就绪的和一个被关掉的（`SearchAPI.Off`，#2286）。刚加的一个排在最后。`ArrangeSearchAPIs` 按点名的厂商给它们排顺序；一个没被点名的在它们之后保留自己的位置，而一个没配好或被点名两次的厂商会拒绝整个顺序，所以从一个在某个被移除之前画出的页面发来的顺序什么也不改变。`SwitchSearchAPI` 设上 `off` 并保留 key、URL 和位置；`SetSearchAPI`（一个新的 key 或 URL）让 `off` 保持原样。一个被关掉的 API 绝不被问，无论是模型的搜索还是搜索 MCP，而在每个 API 都关着时，设置里那行「Search first with」就像一个都没有时那样没了。备份和同步带着 `off` 和这个顺序以及这个条目的其余部分：一次恢复（`RestoreSearchAPIs`）把备份里的 API 按备份的顺序摆好，只在这里的那个排在它们之后，而一个在 `off` 之前做的备份把每个 API 都打开。

在设置 › 模型 › 网页搜索里，每个 API 的行和它的 key 的行作为一个整体移动（`.search-unit`，`searchArrange`）：被它任何一部分从它的按钮和字段上拖走（`dragRows`，和路由的组一样，#779）或用 Alt+↑/↓ 移一格，那些行同时重新编号；一个存不下的顺序按存下的那样重新画出。每一行上的开关发 `{vendor, on}`；一个关掉的变暗并写着 Off。在 CLI 上，`chongyun search off <api>`、`on <api>` 和 `move <api> <n>` 做同样的事，而 `chongyun search` 把一个关掉的列成关掉的。`POST /api/settings/search-api` 接受 `{arrange: [vendors]}` 和 `{vendor, on}`，就在它之前接受的添加和移除旁边。

覆盖的是 `TestSearchAPIOrderAndOff`、`TestSearchCLIOffAndMove`、`TestBackupSearchAPIsOrderAndOff` 和 `search-order.test.cjs`。

## 一个搜索 API 的 key

<a id="a-search-apis-keys"></a>

一个搜索 API 的 `key` 可以装好几个 key，用逗号分隔（#1477）。`askSearchAPIKeys` 按 `searchKeyOrder` 给出的顺序问它们（[`search_keys.go`](../../internal/gateway/search_keys.go)），每个分到这个搜索四分之一的时间。默认它们轮流来（SlouchyQuill 报告，在 dsh-tavily-pool 之后）：每个厂商一个计数器，每次搜索把先被问的 key 往后挪一位。`pick` 为 `order`（`provider.SearchPickOrder`，`chongyun search add … pick=order`，设置里的 In order）总是从第一个开始。只有一次拒绝（`searchRefused`：401、402、403、429、432、433）才走到下一个 key；任何其它错误就在那里结束这个搜索。

一个被拒的 key 会休息（`searchRestFor`）：401 和 403 十分钟（「turned away」），402 一小时（「out of credit」），一个限速按它的 `Retry-After` 限制在 30 秒到 10 分钟之间（没有它就是一分钟）。432 和 433 是 Tavily 的套餐和按量付费限制，只在来自 Tavily 时是额度用尽；来自任何其它厂商时它们作为限速休息。一个在休息的 key 不会被丢掉：它在每个没在休息的 key 之后被问，最早回来的那个先，所以一次搜索仍然有每个 key 可以退到。一个回答了的 key 会醒来。休息按厂商和这个 key 的一个哈希（`searchKeyID`）持有，绝不按 key 本身，而厂商的错误在它被记下或返回之前把 key 打码（`provider.MaskSearchKey`，`tvly-…abcd`）。

一个搜索 API、一个 Kimi Code 套餐的搜索服务或 WorkBuddy 的搜索被问的那个查询，按设置 → 隐私所说的被打码（[`redact.go`](../../internal/gateway/redact.go) 里的 `maskedQuery`；一个被设成不打码的套餐，`provider.SkipsRedaction`，得到它原样的查询）。一个搜索者模型是通过 `serve` 被问的，它照常打码它的请求。一个 agent 对搜索 MCP 的调用带着那些值被放回去的查询，所以在这之前它照 agent 写的样子发出去（lc 报告）；`searchMCPRun` 在它返回的东西里把那些值放回去（`redact.Restore`）。一个模型自己的 web_search 找到的东西照找到的样子回到它的厂商，占位符也在内。

每个 Tavily key 用了多少是用那个 key 从 `GET /usage` 读来的（[`search_quota.go`](../../internal/gateway/search_quota.go)，`readTavilyUsage`）：这个 key 自己的 `limit`，当它有的时候，否则是它那个账户套餐的 `plan_limit` 和 `plan_usage`，由这个账户的 key 共享（一个免费账户的 key 的 `limit` 是 null）；两者都是 null 就是没有限制。一次失败的读或一个缺了那些字段的回复是未知的，带着原因，绝不是「用了 0」。一次读被保留两分钟（Tavily 允许 10 分钟里 10 次 /usage），除非被要求读新的。一个到了自己限制而没有按量付费余额的 key 以「used up」休息一小时；后来一次发现有余额的读会唤醒一个因那个或因额度用尽而休息的 key。设置 › 模型 › 网页搜索在一个有好几个 key 的 API 下面或 Tavily 的下面显示 key 的一行（In turn / In order，每个 key 打码并带着它用了多少，Check again），而 `chongyun search` 列出同样的，读的是新的。

覆盖的是 `TestReadTavilyUsage`、`TestSearchKeysTakeTurnsRoundRobin`、`TestSearchKeyRefusedRests`、`TestSearchRestFor`、`TestSearchQuotas`、`TestSearchKeyNeverInFull`、`TestSearchAPIKeysTakeTurns` 和 `search-keys.test.cjs`。

## 作为 MCP server 的网页搜索

<a id="web-search-as-an-mcp-server"></a>

`SearchMCPPath`，`/mcp/magpie/web-search`，作为一个自己的 MCP server 提供那个不能搜索的模型所得到的同一个 `webSearch`（搜索者的模型、一个 Kimi Code 套餐的服务、那些搜索 API，按设置 › 模型 › 网页搜索的顺序），所以 Cursor、Claude Desktop 或任何 agent 都能把它挂成一个 `web_search` 工具（Kayphoon 报告）。它只说 Streamable HTTP：一条 JSON-RPC 消息或一批的每个 POST 都用 JSON 回答（`initialize`、`ping`、`tools/list`、`tools/call`），通知得到 202，而 GET 和 DELETE 得到 405，因为这个服务器没有自己的流或 session。旧的 SSE 不被服务；一个只说 stdio 的客户端通过 `mcp-remote` 挂它。这个路径在 `/mcp/` 之下有两段，所以它藏不住一个登录态服务器的 `/mcp/{name}`。

它和其它路由一样是一条网关路由。`lanGuard` 从另一台机器取一个网关 key（只在崇云科技被共享时）并拒绝一个 rebounded 的浏览器 host，而在 `Handler` 不带 `lanGuard` 提供服务时，handler 又检查一次 `local`/`sharedWith` 作为兜底。和其它路由不同，这台电脑上的一个网页（一个 `localhost` 的 Origin，`corsGuard` 放它过去）也被拒：只有设置里列出的 origin，而 `corsGuard` 已经把它握在一个网关 key 上，才可以调用它，正如 MCP 规范里服务器对 `Origin` 的检查那样。`keyLimited` 放 `/mcp/` 过去，所以每次 `tools/call` 自己预留调用方 key 的限制（`budget.Reserve`），而一个花完的 key 的调用是一个没有做搜索的工具错误。这个搜索被标为 `CallFor{Agent, MCP: true}`，所以 Routing 说是 agent 调用了崇云科技的 web_search MCP 工具，而不是崇云科技为它自己的某个模型搜了。什么都不会搜索时，那个工具错误说在哪里加一个搜索 API。设置 › 模型 › 网页搜索显示那个地址（`#searchMcpRow`，来自设置页面自己的 `gateway` 地址）。

它的第二个工具 `web_fetch`（`search_fetch.go`，#2286），为一个没有自己 fetch 工具的 agent 按 URL 读一个页面。那个 URL 是 agent 的，所以它像调用方的图像那样被下载（`webFetchClient`，就是 `publicClient`）：只限公网地址，每一个解析出来的地址都被检查并钉住，穿过最多五个重定向而每个也同样被检查，不管请求是从哪里来的。它最多读 30 秒和 5 MiB。一个 HTML 页面从它的 charset 解码并作为 Markdown 给出（`htmlText`：标题、列表、变成绝对地址的链接、代码；脚本、样式和隐藏元素被丢掉），其它文本照原样，任何别的是工具错误，一个 400 或更高的状态也是。它从 `offset` 起回答 `max_chars` 个字符（默认 20000，最多 100000），并说出其余部分从哪个 offset 开始。每次调用像一次搜索那样预留调用方 key 的限制。`TestWebFetchReadsAPage` 和 `TestWebFetchOnlyPublic`。

一个 POST 的 body 由 `readMCPBody` 读，这里最多 1 MiB，而视觉的和登录态服务器的 `/mcp/{name}` 是 32 MiB。一个更长的 body 整个被以 413 拒绝，在它里面任何消息被执行或传下去之前：那个长度是从读到的字节说出来的，比限制多一个，不是从 Content-Length，所以一个合法的但被填充过限制的消息绝不会被当作它的前缀来跑（#1766）。`TestOwnMCPRejectsOversizedBody` 和 `TestMCPProxyRejectsOversizedBody` 覆盖它。

覆盖的是 `TestSearchMCPServesWebSearch`、`TestSearchMCPWithNoSearcher`、`TestSearchMCPGuarded`、`TestSearchMCPHeldToKeyLimit`、`TestSearchMCPRoutedAsTheAgentsCall`、`TestSearchQueryMasked` 和 `search-mcp.test.cjs`。

## 作为 MCP server 的图像识别

<a id="image-recognition-as-an-mcp-server"></a>

`VisionMCPPath`，`/mcp/magpie/vision`，把那个描述图像的模型作为一个带一个 `analyze_image` 工具的 MCP server 提供给一个看不见图像的模型（`seer`：设置 › 模型 › 图像识别，否则是 `AutoVision` 的那个）（JonahFu 报告）。`serveMCP` 与网页搜索的服务器共用，所以它被同样地回答、守卫和做 Origin 检查，body 是 32 MB 以便一张图像能作为 data URL 装下，而每次调用预留调用方 key 的限制（`budget.Reserve`）。那个工具接受 `image` 和一个可选的 `prompt`。没有 prompt 时它像描述一个模型的图像那样被描述（`describe`，同一个缓存和 `visionSystem`）；有 prompt 时 `askVisionWith` 在 `visionAskSystem` 下把那个 prompt 和它一起问。`image` 是一个 http(s) URL 或一个 `data:image/…;base64,` URL，照原样传下去，或一个绝对文件路径（`~/` 和 `file://` 都被处理），当 `http.DetectContentType` 说它是一个图像时被读成一个 data URL，最多 20 MB。一个路径只对一个 `local` 的调用方被读：另一台机器的路径在这里什么也不指，一个共享的崇云科技的文件不是它调用方的，而一个穿过代理或隧道的请求不是 `local`。那个描述的路由被标为 `CallFor{Agent, MCP: true}`，所以 Routing 说是 agent 调用了 analyze_image。图像识别关着或没有会看的模型是一个工具错误，说在哪里挑一个。设置 › 模型显示那个地址（`#visionMcpRow`，在图像生成下面）。

覆盖的是 `TestVisionMCPAnalyzesImage`、`TestVisionMCPWithNoSeer`、`TestVisionMCPGuarded`、`TestVisionMCPHeldToKeyLimit` 和 `vision-mcp.test.cjs`。

## 崇云科技挑的副模型：先看配额

<a id="side-models-magpie-picks-allowance-first"></a>

当崇云科技自己挑模型时（图像识别的 `AutoVision`、网页搜索的 `autoSearcher` 和 `modelSearch` 里的那一轮），它在路由跑之前就挑了，所以路由只有一个 provider 可试，而会在它的每个账户都休息时照样试它。于是每个请求都会在上游再次被拒（#1801）。`spentModel`（fallback.go）说一个模型超出了它的配额，当路由本会为它试的每个候选都被一个用量上限挡住、因配额或额度而休息（不是因限速），或有一个满的窗口（`candidate.full`），并说出它何时回来。`smallModel`（`smallReady`）偏好那些没被用完的模型，而这些挑选者把一个有配额的 provider 排在任何 tier 或 searchRank 之上。当每一个都被用完时它们仍然给出一个挑选，所以 `seer`/`Described` 和 `canSearch`（它们告诉 agent 崇云科技提供什么）不会随着一个窗口而翻转这样一个挑选不会被问：`askVisionWith`（`autoSpent`）用那个理由和它何时回来回答，而 `modelSearch`（`searcherSpent`）跳过它，把用完的搜索者排在其它之后，并把那个理由并进它的错误里。一个在设置里点名的模型照旧被问，而在那里点名的搜索者在失败时不被交给另一个 provider（见「一个失败或什么都没找到的搜索者」）。图像和视频生成（`AutoDrawer`，`AutoVideomaker`）不这样被挡住。

覆盖的是 `TestAutoVisionPassesOverOneOut`、`TestAutoVisionTierAmongThoseWithAllowance`、`TestSpentModelAcrossAccounts`、`TestVisionDoesNotAskSpentDescriber` 和 `TestSearcherPassesOverOneOut`。

## 禁用的模型

<a id="disabled-models"></a>

设置 › 模型 › 禁用的模型、`chongyun model disable|enable|disabled` 和 `POST /api/settings/disabled-models` 保持 `settings.DisabledModels`（#1867）：一些模式，每个是一个确切的 id 或一个 glob（`*` 是任意一串字符，`/` 也在其中；`?` 是一个），忽略大小写地与一个模型的 `<provider>/<model>`、它的裸 id 和那个裸 id 的最后一段匹配（[`internal/provider/disabled.go`](../../internal/provider/disabled.go)）。默认没有任何东西被禁用。

- 列表：`buildEntries`（`entriesOff`）把一个被禁用的模型留在目录之外，于是 `/v1/models`、agent 的模型文件和选择器、Codex 的列表、Muse 和每一个路由组都没有它；`membersIn`（`membersOff`）跳过它作为成员，`Deciders` 跳过它作为决策模型。`codexModels` 丢掉 Codex 自己的一个被禁用的模型，而 `codexListTag` 随那个列表改变，所以 Codex 再取一次。
- 请求：网关以每种 API 的形态用一个 403 拒绝它（[`internal/gateway/disabled.go`](../../internal/gateway/disabled.go)），`model <id> is disabled in chongyun …`，在 #882 把 key 握住的那些咽喉点上：`serve`（每一个 chat、Responses、Messages 和 Gemini 请求，崇云科技自己的副调用，一个曾在它上面的 session，一个被放到它上面的 Codex 子 agent），`perKeyBarred`（不为它规划任何候选：一个组的下一个成员，一个 provider 的 `Fallback`），`countTokens` 和 Gemini 的 `:countTokens`（`countOff`），`serveSystemOne`、`serveDecisionGroup` 和 `postDecide`（每一次决策调用），绘图、视频和 embeddings，以及 `codexBackend` 对 Codex 自己的某个裸模型。一个目录不再有的裸 id 被作为禁用的拒绝，而不是 404（`provider.BareDisabled`）。一个还剩成员的组在没有其余成员的情况下继续；一个一个成员都不剩的组被拒绝，点名它那些被禁用的成员（`provider.GroupDisabledOut`）。一个落到被禁用模型上的 Codex 子 agent 挑选被留在它 lead 的模型上（`codexSubagentPick`，「it is disabled in chongyun」）。
- 一个读不了的 settings.json 绝不是「没有禁用任何东西」：最后读到的那个列表继续生效，而一个从启动起就没读到过任何东西的，每一个请求都被拒绝直到它被修好（`DisabledUnknown`）；`SetDisabledModels` 不在一个它读不了的文件上写任何东西。
- 只覆盖穿过崇云科技的请求：一个自己登录到厂商那里的 agent 不在覆盖之内，设置的那一行这么说。
- 测试：`internal/gateway` 和 `internal/provider` 里的 `TestDisabled*`，`TestModelDisableCmd`，`TestDisabledModelsSetting`，以及 `internal/gui/tests/disabled-models.test.cjs`。

## 不带 provider 的模型 id

<a id="model-ids-without-the-provider"></a>

一个从别的代理搬过来的客户端（love1sbug 报告，从 CLIProxyAPI 来的）一直要求 `gpt-5.6-sol`，并从 `/v1/models` 里挑，而崇云科技在那里只列 `codex/gpt-5.6-sol`。一个裸请求本来就能路由（见上面的模型解析）；是那个列表没有提供它。「Provider in model names」（`PlainNames`）只改标签，绝不改 id。

设置 › 网络与分享 › 不带 provider 的模型 id，`POST /api/settings/bare-ids`（`settings.BareModelIDs`，`provider.SetBareModelIDs`），默认关着。开着时，`models` 先列出它之前列的每一行，不变且在前，然后每个裸模型 id 一行（`provider.BareEntries`，[`internal/provider/bare.go`](../../internal/provider/bare.go)）：那个 id 到达的条目的行，带着它的标签，在那个裸 id 下面。`GET /v1/models/{id}` 同样回答一个裸 id（`provider.BareEntry`）。

- 哪个条目：网关自己的解析，所以那个列表永远不会提供一个请求到不了的条目。一个那个 id 点名的找到的组或用户组（`groupForIn`，与 `GroupFor` 一样）给出那个组的行；否则 `resolveIn`（与 `Resolve` 一样）给出 Providers 顺序里第一个提供它的 provider。所以一个几个 provider 都服务的模型只被列一次，而照旧，开启找到的组时由它的组回答，否则由第一个 provider 回答。
- 一个已经原样在目录里的 id（一个组的或一个 provider 自己的 id）不被列两次。组自己的行什么也不加。
- 目标必须在你看到的那个列表里：一个被限制在某些模型上的网关 key 只看到到达它某一个模型的那些裸 id，所以一个被限制在 `b/*` 上的 key 看不到会走到 `a` 的 `glm-5.3`。
- 绝不给另一个崇云科技（`DrawersHeader`），它的远端 provider 会把每个模型列两次，也绝不给 Claude Desktop 的那个列表，它有自己的形态。
- 没有 agent 文件的改动：崇云科技仍然写 `provider/model` 形式的 id（`magpieModels`），所以把它打开或关掉什么也不重写。
- 测试：`TestBareModelIDsReporterCase`（Codex 的 `gpt-5.6-sol` 被裸列出并在 Chat、Responses 和 Messages 上被回答，关掉时列表不变），`TestBareModelIDsShared`（几个 provider、找到的组开着和关着、一个被限制的 key、另一个崇云科技）在 [`bare_ids_test.go`](../../internal/gateway/bare_ids_test.go) 里，`internal/gui` 里的 `TestBareModelIDsSetting`，以及 `internal/gui/tests/bare-ids.test.cjs`。
- 一个崇云科技下载但不是自己挑的 URL，只从公网地址被下载，不管请求是从哪里来的（[`image_fetch_guard.go`](../../internal/gateway/image_fetch_guard.go)）。那是一个调用方点名的图像（一个 `/v1/images/edits` 或 `/v1/images/generations` 的参考图，给收文件的 images API、Gemini 自己的 API 或 Code Assist：`fetchPicture` 在 [`draw.go`](../../internal/gateway/draw.go)，`publicClient`），一个 `web_fetch` 读的页面（`webFetchClient`），以及一个厂商用 URL 回答的图像或视频，而模型被要求画或做的内容可以左右它（`draw.go` 里为一个 `b64_json` 调用方的内联下载和 [`video.go`](../../internal/gateway/video.go) 里的 `/v1/videos/{id}/content`，`vendorClient`；generate_image 自己的下载在 [`internal/imagemcp`](../../internal/imagemcp/imagemcp.go)，`PublicClient`）。那个 host 解析到的每一个地址都必须是公网的（`publicAddr`：不是回环、RFC 1918、fc00::/7、含 169.254.169.254 的链路本地、CGNAT 100.64/10、未指定、多播、文档、保留、Teredo，也不是其中任何一个的 IPv4-mapped、NAT64 或 6to4 形态），而请求去的是被检查过的那个地址，所以一个第二次解析到别处的名字什么也不改变；一个直连在拨号的地址上又被检查一次（`guardDialer`）。穿过一个代理时，发给代理的是那个地址，绝不是那个名字（一个 `https://` CONNECT 或 SOCKS 为 TLS 和 Host 保留名字；一个普通的 `http://` URL 穿过一个 HTTP 代理时也按 Host 里的那个地址被请求）。每一次重定向，最多 5 次，都同样被检查，而一个调用方的图像必须嗅探成图像。一个来自这台电脑的请求得不到更多：同一个 host 上崇云科技前面的一个反向代理或中继让它带的每个请求都从回环到达，所以请求来自哪里绝不是一个去够私网地址的理由。有两件事是：settings.json 的 `fetchPrivate`（`settings.FetchPrivate`，默认没有，没有设置页面，这台机器自己的，绝不由同步或恢复带进来），一些用户允许崇云科技从中下载的名字、`name:port`、IP 和 CIDR 段的列表（`allowFor`；一个读不了的 settings.json 不让任何额外的东西进来），以及对一个厂商的 URL 那个 provider 自己端点的 `host:port`，那是他自己点名的（一个在 LAN 上、从自己提供图像的 provider）。一个下载不了的厂商图像由它的 URL 回答，绝不被丢掉；它的视频是一个点明原因的 502。一个留给厂商去取的 URL（一个 chat 模型的消息）是厂商去取的。
